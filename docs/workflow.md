# 多窗口协作方式

## 窗口职责

当前窗口保留为项目总控窗口，负责：

- 确认规则和产品需求
- 拆分任务
- 决定任务先后顺序
- 处理不同窗口之间的冲突
- 审核阶段成果
- 更新总体计划
- 组织 GitHub 合并和上线

具体功能应在独立窗口完成，但不建议在 Git 仓库建立前同时开发多个功能。

完整任务顺序以 `docs/TODO.md` 为准。用户不需要自己猜测下一项：每个任务完成后回到项目总控窗口，总控负责验收、合并、勾选任务，并提供下一窗口的完整提示词。

每个“下一项”都应在 `docs/prompts/` 下具有一份可直接复制的详细提示词。提示词必须包含：必读文件、分支名称、任务目标、允许修改、禁止事项、验收命令、文档更新和最终报告格式。

## 新窗口开场模板

在新窗口中发送：

```text
这是永城八张项目的一个独立任务。
请先完整阅读项目根目录的 AGENTS.md、docs/project-status.md、docs/decisions.md，以及与本任务相关的文档。

本窗口唯一任务：<填写任务名称>
允许修改：<填写目录或文件>
不要修改：<填写不在范围内的内容>

开始前先说明你对任务范围、依赖和验收标准的理解。完成后更新 docs/project-status.md 和 docs/TODO.md；如果产生重要取舍，也更新 docs/decisions.md。
```

## 推荐窗口拆分

按下面顺序创建窗口，而不是一次全部打开：

1. GitHub 与工程初始化
2. UI 视觉原型和设计系统
3. 游戏规则引擎及测试
4. 房间与 WebSocket 服务
5. 首页、创建房间和等待房间
6. 游戏牌桌和卡牌交互
7. 三人和四人模式集成
8. 聊天、观战、重连和战绩
9. 测试、部署和上线

## 并行原则

- UI 原型与纯规则测试可以并行，因为文件范围基本不重叠。
- 规则引擎确定前，不应实现完整牌桌业务。
- 共享协议未冻结前，不应同时大规模开发前端和后端联机逻辑。
- 多个窗口需要改同一文件时，改为串行处理。
- GitHub 建立后，每个功能窗口使用独立分支；总控窗口负责审查和合并。

## Git 分支规范

- `main`：始终保存经过验收、可以继续开发的稳定状态。
- `feature/<名称>`：新功能，例如 `feature/game-engine`。
- `design/<名称>`：视觉和交互设计，例如 `design/table-prototype`。
- `fix/<名称>`：缺陷修复。
- `docs/<名称>`：只修改文档的任务。
- 新窗口开始任务前先从最新 `main` 创建自己的分支。
- 一个窗口只在自己的分支提交，不直接覆盖其他窗口分支。
- 功能完成、测试通过并更新项目文档后，再由总控窗口合并到 `main`。
- 未经检查，不使用强制推送，不改写已经推送的公共历史。

## 完成标准

每个功能窗口结束前必须：

1. 完成约定的实现或文档。
2. 运行与任务相称的测试。
3. 报告修改文件和验证结果。
4. 更新项目状态和任务清单。
5. 记录新增的重要决策。
6. 明确指出仍存在的风险或未解决问题。

任务窗口不得自行勾选为最终完成。任务分支通过总控窗口验收并合并到 `main` 后，由总控将对应任务从 `[ ]` 更新为 `[x]`，同时把“下一项”移动到后续任务。
