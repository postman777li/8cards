# 重要设计决策

## 已接受

### D001 项目上下文写入仓库

所有跨窗口需要保留的规则、架构、状态和决定必须写入项目文档，不依赖某一个聊天窗口的历史记录。

### D002 当前窗口作为项目总控

当前聊天窗口负责规划、拆分任务、确认规则、维护总体状态和验收阶段成果。具体功能可以在独立窗口完成。

### D003 统一采用逆时针顺序

二人、三人和四人模式统一使用逆时针座次与操作顺序，减少玩家理解成本。

### D004 服务端权威

洗牌、发牌、行动权限、合法性和胜负全部由服务器决定。客户端不接收对手隐藏信息。

### D005 UI 参考而不复制欢乐斗地主

参考《欢乐斗地主》的成熟交互模式和信息布局，但使用原创品牌与视觉资产，避免复制商标、美术、声音和逐像素界面。

### D006 先规划后开发

规则、产品范围、架构和任务拆分确认前，不进入功能代码开发。

### D007 房间名称和随机短码并存

房间允许玩家填写自定义名称，同时由系统生成随机短码和分享链接。

### D008 第一版访客战绩跟随浏览器

第一版不要求账号登录，战绩跟随浏览器中的访客身份，不承诺跨设备恢复。

### D009 超时自动动作

默认倒计时为 20 秒。进攻方超时自动过牌，防守方超时自动收牌。

### D010 四人采用单人防守和双人进攻

抽到明牌的玩家担任防守方，其对家不能进攻或跟牌；另一队的两名玩家均可按逆时针顺序跟牌。

### D011 四人模式回合与数量限制

防守方的对家完全旁观且不能帮助压牌。两名进攻者都过牌后视为防守成功。防守成功后，原防守方获得下一次进攻权；防守方收牌后，其下一次进攻回合被跳过。四人模式同样采用防守方实时剩余手牌数量限制。

### D012 回合游标统一按玩家座次移动

所有人数模式采用同一回合游标规则。防守成功时，原防守者成为下一轮进攻者；防守者收牌时，跳过该玩家的进攻回合，由下一位玩家进攻再下一位玩家。例如 `A → B → C → D` 中 A 进攻 B，B 收牌后由 C 进攻 D，B 防守成功后由 B 进攻 C。

### D013 工程基础采用轻量 TypeScript 单仓库

使用 Node.js 24 LTS、pnpm workspace、TypeScript 5.9、React 19、Vite 8、Vitest 5、ESLint 10 和 Prettier 3。服务端基础骨架使用 Node 原生 HTTP，不在工程初始化阶段引入 Web 框架、WebSocket 或数据库依赖。TypeScript 暂不采用 7.0，因为当前 `typescript-eslint` 尚未声明兼容。

### D014 UI 采用原创中原夜宴视觉与共享组件分层

第一版 UI 使用深墨绿牌桌、暖金铜色和象牙白卡牌形成“中原夜宴”视觉方向，以原创城墙轮廓、印章和几何纹理表达地域气质，不使用外部商业游戏素材。基础设计令牌及按钮、面板、徽章、座位、扑克牌组件归入 `packages/ui`，场景编排与本地原型交互归入 `apps/web`。合法牌除绿色描边外同时显示“可出”文字，不可用牌降低饱和度和亮度，避免只依赖颜色传达状态。手机横屏优先保留牌桌行动、手牌和核心按钮，允许隐藏次要说明与禁用演示按钮。

### D015 仓库文本文件统一使用 LF

使用 `.gitattributes` 将跨平台文本文件的仓库存储和工作区换行统一为 LF，避免 Windows 的 `core.autocrlf` 在切换任务分支后导致 Prettier 对未改动文件产生格式差异。Word、图片等二进制资产明确标记为 binary。

### D016 共享协议采用版本 1、可判别事件和严格 Zod 校验

共享实时协议从版本 `1` 开始。事件以稳定 `type` 字段区分客户端请求、服务端单播和公共广播；请求使用请求标识关联响应，动作序号为正整数，状态版本为非负整数。采用 Zod 作为唯一网络边界运行时校验工具，由 schema 推导 TypeScript 类型，避免静态类型与运行时模型漂移。所有协议对象使用严格字段策略，未知字段直接拒绝而不静默保留或剥离。

### D017 用独立视图类型固定隐藏信息边界

公共快照、玩家本人视图、对手视图和观战者视图使用不同结构。公共结构只公开手牌数量；只有玩家本人单播视图具有自己的 `private.hand`。服务端权威状态中的全量手牌、牌墩顺序、随机种子、重连令牌和连接标识不属于任何网络事件 schema，防止其被误广播。

### D018 明牌不计入初始手牌

洗牌后，在初始轮抽会经过的牌中预先随机指定一张非王牌作为明牌；随机命中王时重新选择。玩家轮到并抽中该明牌时成为首位防守方，明牌不进入其 8 张初始手牌，而是移至牌墩底部；该玩家立即补抽一张，然后继续原有逆时针轮抽顺序。最终每位玩家恰好持有 8 张，主牌花色由明牌花色确定。

### D019 卡牌基础层采用函数随机源和顶部优先牌墩数组

`game-engine` 复用 `@8cards/shared` 的卡牌结构，通过返回 `[0, 1)` 有限数值的 `RandomSource` 函数注入随机性。洗牌采用不修改输入的 Fisher–Yates；无效随机值明确抛错。牌墩数组约定索引 0 为下一张抽取的顶部，末项为底部，明牌在初始轮抽结束后位于末项。明牌候选限制在原始牌序前 `玩家数 × 8` 张，并按无放回方式随机检查候选；命中王时移除该候选再选，从而保证退化随机源也不会无限循环。`compareCards(left, right, trumpSuit)` 返回 `1`、`0`、`-1` 表示左牌较强、等值、较弱，返回 `null` 表示两个异花色副牌不可比较。

### D020 每轮从主进攻方开始按座次补牌

无论防守成功还是防守方收牌，只要牌墩仍有牌，每轮结束都从本轮主进攻方开始，严格沿统一逆时针座次为所有玩家补牌。仅手牌少于 8 张的玩家抽至 8 张，已经达到或超过 8 张者不抽；牌墩中途耗尽即停止。二人模式自然是进攻方先、防守方后；三人示例 `A → B → C` 中 A 主攻 B 时，补牌为 A、B、C，而不是两名进攻者优先。

### D021 二人引擎采用不可变原子转换与稳定错误码

二人规则状态机以 `awaiting-attack`、`awaiting-defense`、`finished` 可判别联合限制阶段组合，由单一 `applyTwoPlayerAction` 纯函数执行带明确玩家身份的动作。成功转换创建新集合并只递增一次状态版本；过牌或收牌所触发的桌面处理、补牌和角色轮转属于同一原子转换。非法动作抛出带稳定错误码的 `TwoPlayerEngineError`，输入状态不被修改。每次成功转换统一检查牌张守恒，然后按“非空纯王判负优先、空手获胜其次”的顺序检查终局。

其中收牌权限独立于普通行动者游标：只要桌面非空，当前防守方既可在等待压牌时收牌，也可在已经压住全部进攻牌、行动权回到进攻方后主动收牌，以落实“打垮也可以收牌”。非防守方或空桌面收牌均拒绝。

### D022 主 2 交换是整局一次的非回合动作

二人状态显式记录明牌是否已经交换。持有主花色 2 的任一玩家可在未终局且牌墩非空时执行一次交换，不要求其为当前行动者；该动作只交换其手牌与牌墩末项，保持主花色、阶段、当前行动者和攻守角色不变，并像其他成功动作一样递增状态版本和检查终局。全局一次标记避免交换后的主 2 被再次当作可交换明牌。

### D023 多人进攻采用循环游标与连续过牌计数

三人模式的两名进攻者按逆时针座次轮流获得一次进攻机会。过牌只放弃当前机会；若另一名进攻者随后合法出牌，连续过牌计数清零，之前过牌者在游标再次到达时可重新跟牌。只有所有当前进攻者在中间无人出牌的情况下连续过牌，才结束本轮并判定防守成功。该机制未来同样用于四人的两名有效进攻者。

### D024 三人引擎采用独立多人状态与可判别终局结果

三人引擎不包装或伪造二人状态，而是复用卡牌模型、牌力比较和桌面牌对等细粒度规则，独立保存本轮主攻、防守方和进攻游标。每次成功压牌后，游标从刚出牌者沿逆时针跳过防守方；任意合法进攻清零连续过牌数，两次连续过牌完成防守成功结算。两名进攻者共享累计攻击数和防守方实时手牌上限。

补牌固定以结算前本轮主攻为起点，沿完整三人座次补牌，不按进攻阵营分组。终局结果使用 `winner/emptied-hand` 与 `loser/stuck-with-jokers` 两种可判别结构，憋王只记录失败玩家，不推断唯一胜者。终局检查沿稳定座次先检查非空纯王、再检查空手；多个玩家在同一原子转换同时憋王的优先级尚未成为最终规则，任务 10 前仍须复核。

### D025 四人憋王按整队失败结算

四人模式按对面座位组队，即座位 0 与 2 为一队、座位 1 与 3 为另一队。任意玩家率先出完手牌，其整个队伍获胜；任意玩家手牌非空且只剩一个或多个王时，其整个队伍立即失败，另一队获胜。终局结果同时记录触发玩家和获胜、失败队伍，便于结算界面解释原因。
