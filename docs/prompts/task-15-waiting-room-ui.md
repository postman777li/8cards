# 任务 15 等待房间与座位系统提示词

将下面提示词完整复制到新的 Codex 窗口。

```text
你正在处理 E:\8Cards 中的“永城八张在线版”项目。

这是路线图任务 15：等待房间与座位系统。本窗口只能完成任务 15，不得提前实现任务 16 或后续功能。

一、开始前必须完成

1. 完整阅读 `AGENTS.md`、README、`docs/project-status.md`、`docs/TODO.md`、`docs/decisions.md`、`docs/architecture.md`、`docs/requirements.md`、`docs/game-rules.md`、本提示词，以及 `apps/web`、`packages/ui`、`packages/shared`、`apps/server` 中与房间和实时协议相关的源码与测试。
2. 检查 `.codegraph/`；存在则理解代码时先用 CodeGraph，不存在则跳过。
3. 确认 `main` 干净并与 `origin/main` 同步，从最新 `main` 创建 `feature/waiting-room-ui`。
4. 开始前在 `docs/project-status.md` 登记任务 15 正在进行，并先说明连接生命周期、等待房状态模型、房主/准备操作、开始游戏交接、重连方案、响应式布局和测试计划。
5. 不得覆盖其他窗口的未提交改动；发现规则或产品歧义必须记录并向用户确认，不得静默猜测。

二、目标

在任务 14 的真实大厅入口之后实现可联机使用的等待房。创建或加入成功的玩家应看到实时房间状态，包括房间名称、短码、人数模式、座位、昵称、房主、在线状态和准备状态，并能复制安全分享链接。

非房主可以准备/取消准备；房主在人数已满且所有非房主玩家准备后可以开始。所有状态和权限必须以服务端广播为准，客户端不得自行判定成功。

三、连接与状态架构

1. 扩展任务 14 的窄 WebSocket 客户端层，使成功创建/加入后的同一个 socket 持续接收并校验 `state.player`、响应和凭证事件，不能在 React 页面中解析原始消息。
2. 建立明确的客户端会话状态，至少区分连接中、等待房、短暂断线、恢复中、恢复失败和已经开始。
3. 客户端动作序号必须在同一连接上严格递增，请求 ID 唯一；`expectedStateVersion` 使用最新公开实时版本。重复点击不得产生重复请求。
4. 状态更新只接受通过 `@8cards/shared` schema 校验的本人视图；不得把本地猜测覆盖到权威快照。
5. 使用任务 14 已保存的 `roomId/playerId/reconnectToken` 接入任务 13 的 `session.resume`。恢复成功后原子替换本地凭证，并从返回的本人状态继续等待房；旧令牌不得保留为当前令牌。
6. 刷新页面时，如果能明确找到当前房间的本地凭证，应尝试恢复；无凭证、凭证失效或房间不存在时给出友好返回首页路径，不能无限重试。
7. 页面卸载、返回首页、连接替换和失败路径必须清理 socket、监听器、计时与待处理请求。

四、等待房功能

1. 按服务端座位顺序显示配置人数对应的座位；空座、已入座、房主、本人、在线/掉线、已准备/未准备必须清楚区分，不能仅依赖颜色。
2. 显示房间名称、六位短码、二/三/四人模式、20 秒规则、是否允许聊天与观战。任务 15 不提供尚无服务端协议支持的房间配置修改。
3. 非房主显示“准备/取消准备”，调用 `room.ready`；等待响应时禁用，失败后恢复并显示服务端错误。
4. 房主显示“开始游戏”。人数不足或有人未准备时清晰解释不可开始原因；真正能否开始仍由服务端裁决。
5. 收到开始后的 `state.player`（公开 game 非空）时进入“对局已开始，等待任务 16 牌桌界面”的正式占位状态，保持连接与本人视图，不实现卡牌操作。
6. 显示分享链接并支持复制；链接只能包含房间码，绝不能包含令牌、玩家 ID 或手牌。
7. 服务端公开状态中的其他玩家只能显示允许字段；不得从本地存储或消息缓存暴露他人手牌、令牌、牌墩或内部状态。

五、视觉与响应式

1. 复用“中原夜宴”设计令牌和任务 04/14 的共享组件，保持正式产品质量。
2. 桌面端可采用牌桌/座位预览加房间信息区；手机竖屏保持座位和主要动作完整可用；手机横屏优先显示座位、准备和开始状态。
3. 当前用户、房主、掉线玩家、空座和准备状态要有文字或图标双重表达；焦点、键盘操作、加载、错误和减弱动画均可用。
4. 不复制商业游戏受保护素材。

六、范围限制

本任务不实现任务 16 的真实牌桌、手牌选择、出牌/压牌/过牌/收牌/主 2 交换，也不实现聊天消息、观战加入、战绩、数据库、匹配或部署。

允许修改 `apps/web`、必要的 `packages/ui`、相关测试和项目文档。除非真实集成测试证明协议存在阻断问题，不修改服务端、游戏引擎或规则；如遇阻断先报告总控。

七、必须覆盖的测试

1. 创建者和加入者收到广播后都能看到一致房间成员、座位与版本。
2. 非房主准备/取消准备使用正确递增序号和 expectedStateVersion；响应失败不留下错误乐观状态。
3. 房主按钮在人未满、有人未准备和可开始三种状态下信息正确；服务端拒绝会展示稳定错误。
4. 玩家加入、掉线、恢复后 UI 根据新快照更新，座位不丢失。
5. 页面刷新使用保存凭证成功恢复并旋转令牌；旧/错误凭证有明确失败出口，不无限重试。
6. 双连接替换后旧连接的关闭不把新页面显示为掉线。
7. 开始成功后进入任务 16 占位状态，保留安全本人视图且不实现游戏动作。
8. 分享链接及页面文本不含令牌；原始测试消息继续检查他人手牌和秘密泄漏。
9. 重复点击、组件卸载和返回首页不会产生重复动作或悬挂连接。
10. 桌面、手机竖屏和手机横屏没有关键遮挡、水平溢出或不可点击控件。
11. 现有服务端、协议、规则引擎和任务 14 测试全部继续通过。

运行并报告：`pnpm install --frozen-lockfile`、`pnpm typecheck`、`pnpm lint`、`pnpm format:check`、`pnpm test`、`pnpm test:coverage`、`pnpm build` 和 `git diff --check`。

实际启动网页与服务端，至少用两个真实浏览器上下文完成：创建房间、第二人加入、第二人准备、取消准备、重新准备、房主开始、其中一人断线并恢复。检查 `/health`、控制台错误、网络关闭清理和秘密泄漏。分别检查桌面、手机竖屏与手机横屏并将验收截图保存在仓库外。
```
