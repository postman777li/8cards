6. 如果存在不属于本任务的未提交修改，不得覆盖或删除，先报告。

二 本任务边界

实现一个纯服务端、可测试、暂存于内存的房间与访客玩家会话核心。它应能被任务 12 的 WebSocket 层调用，但本任务不建立 WebSocket、房间 HTTP 接口或客户端接入。

本任务负责：创建/加入/离开房间、随机短码、分享路径、昵称、座位、房主、准备状态、开始权限、访客玩家身份、会话鉴权和安全重连令牌。

本任务不负责：真实网络连接、动作序号去重、游戏引擎接入、倒计时、掉线检测、断线保留时长、聊天、观战、战绩、数据库或 UI。任务 13 才实现真实断线重连流程；本任务只提供可供后续使用的令牌签发、校验和会话恢复基础。

三 建议模块边界

1. 在 `apps/server/src` 内建立清晰的房间领域模块，例如 `room-service.ts`，并按需拆分存储、标识生成和错误类型。
2. 房间服务不得持有 HTTP request、WebSocket、socket 或 UI 对象。
3. 默认使用进程内 Map 存储，但通过窄接口隔离，未来能替换数据库而不改变房间业务 API。
4. 所有改变房间状态的操作必须是同步原子转换或具有等效串行保证，不能留下半完成状态。
5. 返回只读快照或防御性副本，不得把内部可变 Map、令牌表或可修改数组暴露给调用者。

四 房间创建与标识

1. 创建房间需要通过共享 schema 验证：
   - 昵称：去除首尾空白后 1 至 24 个字符。
   - 自定义房间名：去除首尾空白后 1 至 40 个字符。
   - 人数：2、3 或 4。
   - `allowSpectators`、`allowChat` 和固定 20 秒配置继续保存，但本任务不实现观战或聊天。
2. 系统生成：
   - 内部 `roomId`。
   - 公开六位大写字母/数字短码，符合现有 `roomCodeSchema`。
   - 创建者 `playerId`。
   - 不可猜测的重连令牌。
3. 短码必须在当前存活房间中唯一；碰撞时重试，并设置明确的最大尝试次数，耗尽后抛出稳定错误，不能死循环。
4. 默认生成器使用 Node 安全随机能力，不使用 `Math.random()` 生成身份或令牌；测试可注入确定性生成器模拟碰撞。
5. 分享地址不硬编码域名。提供稳定分享路径或可传入 base URL 的纯函数，例如 `/room/ABC123`，并正确处理末尾斜杠。
6. 创建者占据座位 0 并成为房主；初始连接为在线。

五 加入、座位与昵称

1. 加入时短码严格规范为现有六位大写字母/数字格式；不要静默接受小写或模糊匹配。
2. 玩家进入当前配置范围内编号最小的空座位。
3. 玩家数量达到 `playerCount` 后拒绝新玩家并返回稳定的房间已满错误。
4. 已开始的房间拒绝新玩家。
5. 昵称不是身份凭证。允许不同玩家使用相同昵称；鉴权只依赖服务端签发的不可猜测令牌。
6. 不得创建配置人数之外的座位；二人房只允许 0、1，三人房只允许 0、1、2。
7. 加入成功返回玩家身份、重连令牌、公开房间快照和当前状态版本；令牌绝不能出现在公开快照中。

六 会话与重连令牌基础

1. 每名玩家拥有独立、不可猜测的当前重连令牌，服务端仅保存适合安全比对的表示；优先保存令牌摘要而不是明文。
2. 房间公开快照、日志、错误详情和序列化结果不得包含令牌、令牌摘要或内部生成状态。
3. 提供按房间/玩家/令牌恢复会话的服务方法，为任务 13 接入断线重连做准备。
4. 成功恢复后旋转令牌：旧令牌立即失效，返回新令牌，防止重放。
5. 错误房间、错误玩家、错误令牌和已离开会话都必须拒绝，且不要通过错误差异泄露令牌是否接近正确。
6. 本任务不实现自动掉线检测或保留期限；可以提供受控的 `markDisconnected` / `markOnline` 领域方法供后续调用，但不能启动计时器。
7. 离开房间后该玩家令牌立即失效。

七 房主、准备和开始权限

1. 只有房主可以开始。
2. 开始前必须恰好达到配置人数，不能少人或超员。
3. 所有非房主玩家必须标记为 ready；房主点击开始本身代表房主确认，不要求房主另行 ready。
4. 玩家只能修改自己的准备状态；房主也可以保存 ready 状态，但开始判定只强制检查非房主。
5. 状态版本不匹配时拒绝带 `expectedStateVersion` 的修改，返回稳定的 stale-state 错误。
6. 开始成功只把房间生命周期标为 started、递增版本并返回用于任务 12 开局的不可变玩家座次与配置；本任务不得调用 `createInitialDeal` 或创建游戏状态。
7. started 后拒绝再次开始、加入、准备状态修改和会改变等待房成员关系的普通操作；是否允许主动离开由实现明确，但不得破坏已返回的开局座次。

八 离开与房主转移

1. 等待房间内普通玩家离开后释放座位并使其会话失效。
2. 房主离开且仍有玩家时，房主转移给当前座位编号最小的剩余玩家。
3. 最后一名玩家离开后销毁房间，短码可在未来重新生成。
4. 离开、房主转移和房间销毁必须是同一次原子操作。
5. 非成员、重复离开或使用失效令牌操作必须返回稳定错误且不改变状态。

九 状态版本与错误

1. 房间创建后的初始版本固定为 0。
2. 每个成功改变公共房间状态的操作恰好递增 1；只读取快照、校验会话或生成分享路径不递增。
3. 恢复会话若改变公开连接状态则递增版本；仅旋转私有令牌而公开状态完全不变时是否递增必须在文档中明确并保持测试一致。
4. 定义服务内部稳定错误码，并提供到 `@8cards/shared` 协议错误码的明确映射。至少区分：输入无效、未授权、房间不存在、房间已满、已开始、非房主、人数不足、玩家未准备、状态过期、短码生成失败。
5. 非法操作不得修改房间、版本、成员、座位、房主或令牌。

十 共享类型的最小调整

1. 优先复用 `@8cards/shared` 已有品牌 ID、schema 和房间公开类型。
2. 如果房间生命周期或服务错误映射需要扩展共享类型，可以做最小兼容修改，并增加 schema 正反测试。
3. 不得向公共 schema 添加重连令牌、连接 ID、内部 Map、随机状态或未来对手手牌。
4. 不得为方便服务端而放宽现有严格 schema。

十一 必须覆盖的测试

1. 创建：输入修剪与校验、2/3/4 人配置、座位 0、房主、版本 0、六位短码、分享路径。
2. 碰撞：短码碰撞重试成功、重试耗尽稳定失败、失败不留下半创建房间。
3. 加入：按最小空座加入、二/三/四人容量、房满、未知短码、已开始房间、严格大小写。
4. 昵称：重复昵称可加入，但玩家 ID 和令牌不同；昵称不能用于鉴权。
5. 准备与开始：本人准备、错误身份、过期版本、非房主开始、人数不足、非房主未准备、合法开始、重复开始。
6. 离开：普通玩家释放座位、后来者复用最小空座；房主转移；最后一人离开销毁房间；旧令牌失效。
7. 会话：正确令牌恢复并旋转、旧令牌重放失败、错误令牌/玩家/房间统一拒绝、公开快照不泄露任何令牌材料。
8. 连接状态：受控标记掉线/上线，不启动真实计时器；版本语义符合文档。
9. 不可变性：外部修改返回对象、数组或配置不能污染服务内部状态；每条失败路径状态完全不变。
10. 并发或重入边界：至少证明同一版本的两次冲突修改只能有一次成功，另一次因版本过期失败。
11. 共享 schema：若有调整，覆盖有效数据和敏感字段、未知字段、非法生命周期的拒绝。
12. 健康检查与此前 168 项测试必须继续通过，规则引擎覆盖率门槛不得下降。
