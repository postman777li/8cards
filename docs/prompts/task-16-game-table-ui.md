# 任务 16 游戏牌桌与卡牌交互提示词

将下面提示词完整复制到新的 Codex 窗口。

```text
你正在处理 E:\8Cards 中的“永城八张在线版”项目。

这是路线图任务 16：游戏牌桌与卡牌交互。本窗口只能完成任务 16，不得提前实现任务 17 或后续功能。

一、开始前必须完成

1. 完整阅读 `AGENTS.md`、README、`docs/project-status.md`、`docs/TODO.md`、`docs/decisions.md`、`docs/architecture.md`、`docs/requirements.md`、`docs/game-rules.md`、本提示词，以及 `apps/web`、`packages/ui`、`packages/shared`、`packages/game-engine`、`apps/server` 中与玩家视图、游戏动作和二人规则相关的源码与测试。
2. 检查 `.codegraph/`；存在则理解代码时先用 CodeGraph，不存在则跳过。
3. 确认 `main` 干净并与 `origin/main` 同步，从最新 `main` 创建 `feature/game-table-ui`。
4. 开始前在 `docs/project-status.md` 登记任务 16 正在进行，并先说明二人牌桌布局、权威状态映射、选牌和动作交互、倒计时、断线恢复、结算占位和测试计划。
5. 不得覆盖其他窗口的未提交改动；发现协议或规则歧义必须记录并向用户确认，不得静默猜测。

二、目标与范围

实现正式质量的二人游戏牌桌，使两名远程玩家可以从任务 15 的等待房开局后，通过网页完成一整局游戏。

必须展示本人手牌、对手牌数、桌面攻防牌、牌墩余量、主花色与明牌、进攻方、防守方、当前行动者、20 秒倒计时、连接状态及服务端允许的操作。客户端只能显示和提交服务端权威视图与动作，不得自行洗牌、判定牌力、修改手牌、推进回合或判定胜负。

任务 16 重点完成二人模式。三人和四人的完整座位、跟牌顺序、队友标识与响应式适配属于任务 17；如果三/四人房开局，本任务应显示安全、清楚的“多人牌桌将在任务 17 完成”占位，不能错误套用二人交互。

三、实时客户端扩展

1. 在任务 15 的持续会话对象中增加 `game.action` 请求能力，保持同一连接严格递增 actionSequence、唯一 requestId 和最新 expectedStateVersion。
2. 动作参数必须使用 `@8cards/shared` 的现有类型与 schema；不得复制一套不一致的前端动作模型。
3. 同一时刻只允许一个游戏动作在途。成功响应本身不乐观改变牌局，界面等待后续权威 `state.player`；失败保留原快照并显示稳定错误。
4. 继续支持刷新和短暂断线后的 `session.resume`，恢复后同步本人最新手牌、桌面、deadline 和合法动作。
5. 旧连接、旧快照和较低版本事件不能覆盖当前会话。组件卸载、身份替换和返回安全页面时清理监听器与待处理操作。
6. 任何日志、错误、DOM、分享链接和其他玩家视图不得包含重连令牌、对手手牌、牌墩顺序或内部权威状态。

四、权威状态展示

1. 本人手牌只能来自 `PlayerView.private.hand`。使用共享扑克牌组件，普通牌明确显示点数和花色，大小王可区分；红黑花色不能只靠细微颜色差异。
2. 按稳定规则排序仅影响本地展示，不改变服务器牌 ID 或动作语义。刷新/广播后选中的已不存在或不再合法的牌必须自动取消。
3. 对手只显示昵称、座位、在线状态、剩余牌数及公开身份，绝不能显示其手牌内容。
4. 桌面按攻牌与对应防守牌配对展示；未被压住的攻牌需要清晰标识。不得仅用数组下标猜测未被防守关系，应按共享公开桌面结构渲染。
5. 显示主花色、公开明牌、牌墩余量、当前阶段、当前行动者、进攻/防守身份与回合结果。所有文案应使用普通玩家能理解的中文。
6. `turnDeadline` 使用客户端当前时间渲染剩余秒数，但不得改写 deadline 或在本地代替服务器执行超时动作。倒计时归零后显示“等待服务器处理”，直到收到新版本。

五、选牌与操作

1. 手牌支持鼠标点击、触屏点击和键盘可访问选择；选中状态明显，不能只依赖颜色。第一版动作逐张执行，因此同一时刻最多选择一张牌。
2. 操作按钮必须根据 `private.legalActionTypes`、当前选择和公开阶段生成，至少覆盖：
   - `play-card`：进攻出牌；
   - `beat-card`：防守压牌；
   - `pass`：进攻方过牌；
   - `collect`：防守方收牌，包括打垮后仍可收牌；
   - `exchange-trump-two`：持主 2 玩家交换明牌。
3. 出牌/压牌时提交选中牌的精确 cardId；禁止状态要解释原因，例如“请选择一张牌”“等待对方操作”或“此牌不能压过当前牌”。客户端可以依据服务器给出的合法动作种类控制入口，但不得自行宣称某张牌合法；若协议没有逐牌合法列表，应允许服务端最终裁决并友好显示错误。
4. 提交期间禁用重复动作并显示处理中。服务器拒绝后保持选择和权威快照，便于玩家重新选择或重试。
5. 主 2 交换不重置客户端倒计时；只接受服务器广播的原 deadline。
6. 收到新权威版本后清理已经成功打出的选择；其他广播不应无故清除仍存在且仍可操作的选择。

六、终局与异常状态

1. 收到 finished 结果后停止提供游戏动作，显示胜负、空手或憋王原因以及返回/后续结算提示；正式战绩和完整结算属于任务 18。
2. 断线、恢复中和恢复失败状态必须覆盖牌桌并防止提交动作；恢复成功后回到最新权威牌局。
3. 已开始游戏不支持普通 `room.leave` 时，不得清除仍可用于恢复的凭证或伪装离房成功。
4. 对局过程中刷新浏览器必须能够恢复本人身份与最新手牌。

七、视觉与响应式

1. 复用任务 04 的“中原夜宴”设计系统、扑克牌和座位组件，参考成熟斗地主牌桌的信息层级与操作节奏，但保持原创视觉素材。
2. 桌面端牌桌需要清晰区分对手区域、中央桌面区、本人手牌区和操作区。
3. 手机横屏是牌桌主要移动布局：核心状态、手牌、桌面和动作按钮必须同时可用，无关键遮挡或水平页面溢出。
4. 手机竖屏允许提示建议横屏，但仍须能够看清状态并完成基本操作，不能完全阻断。
5. 当前行动者、合法操作、选中牌、倒计时最后 5 秒和网络状态必须有文字/图标辅助，不得只依赖颜色或动画。
6. 遵守减弱动画偏好，不使用商业游戏受保护素材。

八、必须覆盖的测试

1. 二人开局后双方视图正确：本人仅见自己手牌，对手只见牌数；DOM 和原始消息无隐藏信息泄漏。
2. 手牌渲染、稳定排序、单牌选择、取消选择及新快照清理无效选择。
3. 进攻出牌、防守压牌、进攻过牌、防守收牌，以及打垮后收牌均通过真实客户端动作路径完成。
4. 主 2 交换提交正确，成功后 deadline 不变。
5. actionSequence 和 expectedStateVersion 严格正确；重复点击只有一个请求；失败不产生乐观状态。
6. 倒计时显示以同一权威 deadline 为准，归零不在客户端执行动作，新版本到达后更新。
7. 当前非行动者、无合法动作、未选牌和服务器拒绝时按钮状态与错误说明正确。
8. 刷新、断线、恢复后本人手牌、桌面、选择、版本和 deadline 与服务器一致；恢复期间无法出牌。
9. 终局后禁用动作并正确显示普通胜负与憋王结果。
10. 三/四人已开局只显示安全占位，不错误暴露或提交二人操作。
11. 至少完成一局二人真实 WebSocket 网页对局，覆盖多个攻防回合、补牌、收牌或防守成功、轮转和终局；不得只靠伪造组件数据。
12. 桌面、手机横屏和手机竖屏无关键遮挡；现有 220 项及全部回归测试继续通过。

九、允许修改与禁止事项

允许修改 `apps/web`、必要的 `packages/ui`、相关测试和项目文档。只有真实集成证明共享协议缺少完成二人牌桌所必需的安全公开字段或动作时，才允许做最小共享协议/服务端修复，并必须记录原因和回归测试。

不得修改游戏规则语义，不得把完整引擎状态发送给客户端，不得提前实现任务 17 的完整三/四人牌桌、任务 18 的聊天/观战/战绩、数据库或部署。
```
