```text
你正在处理 E:\8Cards 中的“永城八张在线版”项目。

这是路线图任务 12：WebSocket 实时游戏服务。本窗口只能完成任务 12，不得提前实现任务 13 或后续功能。

一 开始前必须完成

1. 完整阅读 `AGENTS.md`、README、`docs/project-status.md`、`docs/TODO.md`、`docs/decisions.md`、`docs/architecture.md`、`docs/requirements.md`、`docs/game-rules.md`、`docs/game-engine-acceptance.md`、本提示词，以及 `packages/shared`、`packages/game-engine`、`apps/server` 的相关源码和测试。
2. 检查 `.codegraph/`；存在则理解代码时先用 CodeGraph，不存在则跳过。
3. 确认 `main` 干净且与 `origin/main` 同步，从最新 `main` 创建 `feature/realtime-server`。
4. 在 `docs/project-status.md` 登记任务 12 正在进行，并先向用户说明协议边界、连接身份、动作顺序、公开版本、状态投影和集成测试方案。
5. 遇到其他窗口修改不得覆盖；发现规则或协议歧义不得静默猜测。

二 目标与边界

在现有 Node HTTP 服务上增加 WebSocket 实时层，把任务 11 房间服务与二、三、四人权威游戏状态机连接起来，使多个真实 WebSocket 客户端可以创建/加入房间、准备、由房主开始、接收按权限裁剪的状态，并顺序提交游戏动作。

本任务实现：WebSocket 升级与生命周期、严格消息解析、连接身份、房间命令、游戏初始化、动作映射、动作序号、请求幂等、乱序/过期保护、按权限单播和公开广播、多客户端集成测试。

本任务不实现：20 秒计时器、超时自动动作、真实断线保留/恢复流程、自动重连、聊天、观战、战绩、数据库或网页接入。连接关闭时只做任务 13 可接管的最小清理，不启动定时器，也不要擅自让玩家永久离开房间。

三 WebSocket 与服务器结构

1. 使用维护良好的 Node WebSocket 库，优先 `ws`，锁定与当前 Node/TypeScript 兼容版本。
2. 复用现有 HTTP server，在明确路径（建议 `/ws`）处理升级；`GET /health` 必须继续正常。
3. 将服务器构造改为可注入依赖和随机源，测试能监听随机端口并可靠关闭所有连接、WebSocket server 和 HTTP server。
4. 限制消息大小，拒绝二进制消息、无效 UTF-8/JSON、超大消息和 schema 不合法数据；这些错误不得导致进程崩溃。
5. 对每条入站消息只解析一次，并通过 `@8cards/shared` 的严格 schema 验证，未知字段不能静默接受。
6. 不记录完整消息、手牌或重连令牌；日志只允许安全的请求 ID、房间 ID、事件类型和错误码。

四 协议最小扩展与凭证交付

1. 复用现有 `ClientEvent`、`IndividualServerEvent`、`PublicServerEvent`，只做任务必需的最小兼容扩展。
2. 创建或加入成功后，浏览器必须收到 `roomId`、`playerId` 和重连令牌。新增严格的单播凭证事件（名称自洽，例如 `session.established`），只发给发起连接。
3. 重连令牌允许存在于该一次性单播凭证事件中，但绝不能出现在：
   - 公共状态或公共广播。
   - 其他玩家的单播状态。
   - 日志、错误详情和测试快照泄漏输出。
4. 新增 schema 正反测试：合法凭证事件通过；放入公共事件、未知字段或错误 ID/令牌被拒绝。
5. 任务 13 才增加恢复连接请求和真实断线流程；本任务只负责初次凭证交付。

五 连接身份与房间命令

1. 新连接初始未认证，只允许 `room.create` 或 `room.join`。
2. 创建/加入成功后，该 socket 绑定唯一 roomId/playerId；同一 socket 再次创建或加入必须拒绝。
3. 后续 `room.ready`、`room.leave`、`room.start` 和 `game.action` 必须使用 socket 绑定身份，客户端不能伪造 playerId。
4. 调用任务 11 RoomService，并将稳定领域错误映射为现有协议错误。
5. `room.leave` 成功后解除连接身份；若房间销毁则清理实时房间状态。
6. `chat.send`、`spectate.join`、`spectate.leave` 在本任务明确返回稳定的未实现/非法操作错误，不要悄悄忽略，也不要提前实现。
7. socket 关闭不能自动永久移除玩家；只移除连接绑定。真实掉线标记、保留座位和恢复由任务 13 实现。

六 请求 ID、动作序号与幂等

1. 每个连接的 `actionSequence` 从 1 开始，成功或业务失败的已处理请求都按明确规则推进；在文档中固定该语义。
2. 正常新请求必须严格等于下一序号；更大序号视为乱序，更小序号视为重复或过期。
3. 以 `requestId` 和序号共同防止重复执行：完全相同请求重发时返回缓存的原单播响应，不得再次改变房间或游戏状态。
4. 相同 requestId 携带不同内容、相同序号换 requestId、重复旧序号或跳号必须返回稳定错误，不能重放动作。
5. 幂等缓存必须有明确上限和清理策略，不能随连接寿命无限增长。
6. `expectedStateVersion` 必须在业务转换前校验。过期请求返回 `STALE_STATE` 且不改变状态。

七 开局与统一实时版本

1. 等待房期间，实时公开版本与 RoomService 的公开 `stateVersion` 一致。
2. 房主合法 `room.start` 后：
   - 按座位号升序取得玩家 ID，作为引擎严格逆时针座次。
   - 使用安全随机源调用 `createInitialDeal`。
   - 根据 2/3/4 人选择正确的 `createTwoPlayerState`、`createThreePlayerState` 或 `createFourPlayerState`。
   - 保存服务器内部权威游戏状态，绝不直接广播。
3. 实时层维护独立单调 `stateVersion`：开始后的初始快照使用开始成功后的房间版本；每个成功游戏动作恰好 +1。不要假定它等于引擎内部 version。
4. 游戏创建失败必须原子处理，不能向部分连接广播“已开始”但没有游戏；如 RoomService 当前接口无法回滚，先设计并测试安全的编排顺序或做最小兼容调整。
5. 同一房间只允许创建一个游戏，重复开始不得重新洗牌。

八 游戏动作映射

1. 只允许已开始房间内的玩家提交 `game.action`。
2. 将共享动作映射到当前模式引擎：
   - `play-card` → `attack`
   - `beat-card` → `defend`
   - `pass` → `pass`
   - `collect` → `take`
   - `exchange-trump-two` → 同名交换动作
3. `beat-card.targetCardId` 必须等于当前唯一待防守的进攻牌，错误目标拒绝；不能只忽略字段。
4. playerId 永远取 socket 绑定身份，不从动作体推断。
5. 引擎错误映射为稳定协议错误，至少区分错误行动者、非法动作和过期状态；失败不递增实时版本、不广播新状态。
6. 成功动作原子替换权威状态，实时版本 +1，然后向相关连接发送新视图。
7. 终局后所有游戏动作由引擎拒绝，服务端不能吞掉错误或另行修改胜负。

九 状态投影与隐藏信息

1. 建立单一、可测试的服务器状态投影层，把 RoomSnapshot 和二/三/四人引擎状态转换为共享 `PublicSnapshot`、`PlayerView`。
2. 公开信息包括房间、模式、主牌、明牌/当前底牌的规则允许展示值、牌墩数量、桌面牌、每人手牌数量、攻守/旁观角色、当前行动者和胜者。
3. 本任务没有倒计时，`turnDeadline` 必须为 null。
4. 每名玩家只收到自己的完整手牌和可用动作种类；不能收到他人手牌、牌墩顺序、随机状态、令牌摘要或其他连接 ID。
5. 合法动作种类必须由当前权威状态与身份推导，不要简单给所有玩家全部按钮；具体合法卡牌仍由客户端提示层后续处理，服务器始终再次校验。
6. 对每个出站状态先用共享 schema 验证再发送。schema 不匹配视为服务端错误并在测试中暴露，不能 `as` 强制掩盖。
7. 广播时逐连接生成视图，禁止复用包含某玩家手牌的对象发送给别人。

十 消息发送顺序

1. 每个请求先向发起者发送关联 requestId 的 `response.ok` 或 `response.error`。
2. 创建/加入成功额外向发起者发送一次性凭证事件。
3. 会改变公开状态的成功请求随后向房内在线连接发送最新状态；每个玩家获得自己的 `state.player` 视图。
4. 不改变状态的重复请求只能重发缓存响应，不重复广播状态或凭证；凭证事件不得因普通网络重试被广播给其他人。
5. 明确并测试同一连接上的事件顺序，防止前端偶发先收到新状态再收到请求结果。

十一 必须覆盖的集成测试

1. 启动真实 HTTP + WebSocket server，确认 `/health` 与 `/ws` 同时可用并能可靠关闭。
2. 非法传输：错误路径、二进制、坏 JSON、超大消息、未知字段、错误协议版本，服务器不崩溃并返回/关闭为预期结果。
3. 身份：未认证连接只能创建/加入；绑定后不能换身份；客户端不能替其他玩家准备、开始或行动。
4. 二人完整接入流程：两个真实客户端创建/加入、访客收到各自不同凭证、非房主准备、房主开始、双方收到同版本但不同私有手牌的状态。
5. 三人和四人分别完成开局，验证座位顺序、首位攻防角色、各玩家只收到自己的手牌；四人对家与旁观角色正确。
6. 至少完成一个真实二人多动作回合：合法进攻、防守、过牌或收牌，所有客户端版本一致且桌面/手牌数量一致。
7. 对三人或四人至少验证另一进攻者能按游标合法跟牌，旁观者动作被拒绝。
8. 隐藏信息专项：检查每个原始 WebSocket 消息，任何连接都不能找到其他玩家的卡牌 ID、完整牌墩或令牌。
9. 幂等：完全相同请求重发不重复执行；同 ID 不同内容、同序号不同 ID、旧序号、跳号均拒绝。
10. 过期版本、错误行动者、错误 targetCardId 和非法牌均失败且所有客户端状态版本不变。
11. 客户端断开不会自动从等待房永久移除玩家；本任务不执行任务 13 的重连计时。
12. 既有房间服务 14 项、全仓 182 项及规则引擎覆盖率全部继续通过。

十二 安全与资源限制

1. 使用安全随机源洗牌，不使用可预测的 `Math.random()`。
2. 限制单连接消息大小、幂等缓存大小和房间连接集合；移除关闭 socket，防止内存泄漏。
3. 任何解析或业务异常都必须转为稳定错误或受控关闭，不能形成未处理 Promise rejection。
4. 测试不得打印真实重连令牌或完整手牌；断言失败信息应避免泄密。
```
