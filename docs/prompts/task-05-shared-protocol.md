二 本任务目标

在 `packages/shared` 中建立前端、服务端和未来游戏引擎共同使用的领域类型与实时通信协议。协议必须清楚表达数据含义、消息方向、成功与失败结果，以及玩家本人、对手和观战者分别能够看到什么。

本任务只建立共享契约和验证工具，不建立网络连接，不实现房间业务，也不实现任何游戏规则。

三 必须定义的领域模型

1. 基础标识与通用字段
   - 玩家、房间、对局、连接或请求所需的标识类型。
   - 协议版本、状态版本或动作序号所需字段。
   - 时间戳和可复用的错误结构。
2. 玩家和房间
   - 昵称、座位、房主、在线或掉线状态、准备状态。
   - 二人、三人、四人模式。
   - 自定义房间名、随机短码、允许观战、允许聊天、20 秒倒计时等配置。
   - 玩家身份与观战者身份应是可区分的类型。
3. 卡牌及游戏公开信息
   - 54 张牌所需的花色、点数、大小王和卡牌标识。
   - 主牌、牌墩剩余数量、桌面牌、当前阶段、行动者、攻守身份、队伍、倒计时截止时间等公开状态结构。
   - 这里只建模，不实现洗牌、牌力比较、合法性或胜负规则。
4. 私有信息
   - 当前玩家自己的手牌及只对本人可见的数据结构。
   - 服务端内部权威状态不得被误当作可广播给客户端的公开状态。
5. 动作
   - 创建或加入房间、离开、准备、开始、聊天及观战所需动作。
   - 游戏动作至少为后续出牌、压牌、过牌、收牌、主 2 换明牌预留明确联合类型。
   - 动作中包含请求标识及防重复或乱序所需的状态版本/动作序号。
6. 错误
   - 使用稳定、可判别的错误码联合类型。
   - 至少覆盖格式错误、未授权、房间不存在、房间已满、行动者错误、动作非法、状态过期、重复请求和服务端内部错误等类别。

四 客户端与服务端事件协议

1. 明确区分：
   - 客户端发送给服务端的事件。
   - 服务端发送给单个客户端的事件。
   - 服务端可广播的公开事件。
2. 采用可判别联合类型，例如每个事件都有稳定的 `type` 字段；具体命名可根据仓库风格确定。
3. 请求和响应应能通过请求标识关联。
4. 状态快照和增量事件都要携带必要的状态版本，避免未来重复和乱序处理时重新破坏协议。
5. 必须提供明确的解析或校验入口，网络边界收到的 `unknown` 数据未经成功校验不得被当作可信事件使用。
6. 若引入运行时校验库，先评估是否确有必要，保持依赖轻量，并把选择与理由记录到 `docs/decisions.md`。
7. 导出组织应清晰，避免所有实现堆在一个超大文件；同时保留稳定的 `@8cards/shared` 公共入口。

五 隐藏信息和权限边界

1. 公共房间或牌桌状态不得包含任何玩家的实际手牌。
2. 玩家视图只能附带该玩家自己的手牌，不能附带对手或队友的手牌。
3. 观战者视图不能包含任何未公开手牌，也不能通过可选字段、嵌套服务端状态或事件载荷意外泄露。
4. 重连令牌、内部连接标识、服务端完整牌序和随机种子等敏感字段不能进入公共广播模型。
5. 优先通过不同的数据结构表达权限边界，不要只依赖开发者记住在运行时删除字段。
6. 用自动化测试证明玩家视图、对手可见视图和观战者视图的结构边界。

六 运行时校验与测试

1. 为所有会跨越网络边界的客户端和服务端事件提供运行时校验。
2. 测试至少覆盖：
   - 每类关键事件的有效样例可以通过。
   - 缺失必填字段、未知事件类型、错误枚举值和错误字段类型被拒绝。
   - 额外敏感字段不能静默进入已验证的公共或观战数据；应拒绝或严格剥离，并由测试固定行为。
   - 玩家本人可接收自己的私有手牌，对手和观战者结构不能携带该信息。
   - 客户端事件联合类型和服务端事件联合类型都可按 `type` 穷尽收窄。
   - 请求标识、版本号或动作序号的非法边界值被拒绝。
3. 测试使用最小、可读的构造样例；不得借测试实现游戏规则。
4. 保持类型和运行时模型一致，避免重复定义后出现漂移；如果必须重复，需有测试保障。
