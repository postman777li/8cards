6. 如果存在不属于本任务的未提交修改，不得覆盖或删除，先报告。

二 本任务定位

本任务是任务 06 至 09 的规则引擎总验收，不是新增一种玩法。目标是把 Word 规则、`docs/game-rules.md` 和用户确认的边界条件整理为可追踪测试矩阵，补齐遗漏测试，并通过大量可复现的合法随机对局发现死循环、牌张丢失、重复牌、错误行动权或非法终局。

发现明确实现缺陷时，可以在 `packages/game-engine` 内做最小修复并添加回归测试。遇到规则歧义时不得猜测或自行确定：写入 `docs/project-status.md`，停止依赖该规则的部分并在最终报告中交给总控确认。

三 规则权威与测试矩阵

1. 权威顺序严格遵守 `AGENTS.md`：最新已确认规则文档、已接受决策、原始 Word、最后才是合理推测。
2. 新建一份规则验收矩阵文档，建议为 `docs/game-engine-acceptance.md`。
3. 矩阵至少逐项覆盖：
   - 54 张牌唯一性、牌 ID、牌力、主牌与王。
   - 可注入随机源、洗牌、非王明牌、初始轮抽、明牌归底和主 2 交换。
   - 二、三、四人首攻、跟牌点数、逐张攻防、非法压牌、王不能进攻。
   - 任意时刻收牌，包括未压、压一张和压多张后收牌。
   - 过牌、连续过牌清零、多人进攻游标和错误玩家权限。
   - 防守方实时剩余手牌造成的累计攻击数量上限。
   - 防守成功与收牌后的补牌顺序、短牌墩和回合轮转。
   - 二人独立胜负、三人独立胜负、四人团队胜负及憋王优先。
   - 每次成功动作的版本递增、54 张牌守恒和输入不可变。
   - 非法动作的稳定错误码、状态不变及终局后拒绝动作。
   - 公共入口和生成的类型声明可用。
4. 每条规则标明已有测试位置、是否新增测试、验证结果和仍存风险，不能只写“已覆盖”。

四 确定性随机对局模拟

1. 为二人、三人、四人分别建立合法动作生成器和可复现的有种子伪随机源。
2. 模拟必须只通过公开初始化与动作 API 推进，不能直接修改状态来伪造成功。
3. 每个模式至少运行 100 个不同种子；数量可增加，但测试总时长应适合日常 CI。
4. 每局设置明确、合理的最大动作步数。超过上限必须使测试失败并报告种子、模式、步骤和最后状态摘要，不能静默截断或把它算作成功。
5. 合法动作生成器必须覆盖：
   - 进攻、压牌、过牌和收牌。
   - 有条件时执行主 2 交换。
   - 多人进攻者轮换和旁观者无行动权。
6. 为避免生成器永远选择收牌或过牌，可以使用带权选择；但不得绕过状态机规则。
7. 每次成功转换后至少验证：
   - 54 张牌无重复、无遗漏。
   - 状态版本恰好递增 1。
   - 输入状态未被修改。
   - actor、阶段和角色组合合法。
   - 桌面牌对结构合法，等待进攻时不存在未防守牌，等待防守时只有最后一对未防守。
   - 攻击累计数、连续过牌数和游标处于允许范围。
8. 随机模拟必须固定种子集合、可重复运行、不依赖网络、系统时间或 `Math.random()` 的不可控结果。
9. 若某些合法策略可能无限互相过牌，动作生成器应保证公平进展，但不能掩盖状态机自身的死循环或错误轮转。

五 憋王与终局专项

1. 验证普通合法转换中，每个会减少手牌的原子动作最多影响一名玩家，因此不会在同一转换中新产生多个憋王玩家。
2. 验证非空纯王判负优先于空手获胜，空手不属于憋王。
3. 验证二人、三人的个人结算和四人的整队结算含义不同且结果字段正确。
4. 稳定座次扫描只作为人工损坏状态或未来批量动作的确定性防御，不把它描述为新的正式玩法规则。
5. 每种模式终局后所有普通动作与主 2 交换均被拒绝，输入状态不变。

六 覆盖率

1. 为 Vitest 增加适合当前版本的 V8 覆盖率支持，并提供根命令，例如 `pnpm test:coverage`。
2. 覆盖率范围聚焦 `packages/game-engine/src` 的生产代码，排除测试、生成声明和构建产物。
3. 游戏引擎整体最低门槛：语句、行和函数不低于 90%，分支不低于 85%。如果当前基线已经更高，应使用不低于实际稳定值的门槛，避免无意义降低。
4. 不得通过大范围 ignore、排除核心文件或只测实现细节来虚增数字。
5. 报告最终四项覆盖率及最薄弱的核心文件；对未覆盖分支说明原因或补测试。
