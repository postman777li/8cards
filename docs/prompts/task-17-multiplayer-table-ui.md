# 任务 17 多人牌桌与响应式适配提示词

将下面提示词完整复制到新的 Codex 窗口。

```text
你正在处理 E:\8Cards 中的“永城八张在线版”项目。

这是路线图任务 17：多人牌桌与响应式适配。本窗口只能完成任务 17，不得提前实现任务 18 或后续功能。

一、开始前必须完成

1. 完整阅读 `AGENTS.md`、README、`docs/project-status.md`、`docs/TODO.md`、`docs/decisions.md`、`docs/architecture.md`、`docs/requirements.md`、`docs/game-rules.md`、本提示词，以及 `apps/web`、`packages/ui`、`packages/shared`、`packages/game-engine`、`apps/server` 中与三/四人规则、投影、动作和牌桌相关的源码与测试。
2. 检查 `.codegraph/`；存在则理解代码时先用 CodeGraph，不存在则跳过。
3. 确认 `main` 干净并与 `origin/main` 同步，从最新 `main` 创建 `feature/multiplayer-table-ui`。
4. 开始前在 `docs/project-status.md` 登记任务 17 正在进行，并先说明三人/四人座位布局、进攻游标与队伍映射、共享牌桌交互、响应式策略、隐藏信息和测试计划。
5. 不得覆盖其他窗口的未提交改动；发现协议或规则歧义必须记录并向用户确认，不得静默猜测。

二、目标

将任务 16 的权威网页牌桌扩展到三人和四人，使二、三、四人三种模式均可从浏览器完成整局游戏。

三人模式各自为战，两名进攻者按权威游标依次获得机会；四人模式为固定对家，防守方的对家是旁观位，另一队两名玩家才是进攻者。客户端只解释服务端视图、突出当前行动者并提交服务端允许的动作，不能自行推进游标、推断下一行动者或计算胜负。

三、统一牌桌架构

1. 重构任务 16 牌桌为可复用的二至四人布局和动作层，避免复制三套相互漂移的牌桌。
2. 保留任务 16 已验证的持续 WebSocket 会话、严格序号、最新版本、单动作在途、权威快照、倒计时、恢复遮罩和隐藏信息边界。
3. 本人手牌始终只来自 `PlayerView.private.hand`；其他所有玩家只能显示公开昵称、座位、连接状态、角色、队伍和牌数。
4. 座位必须依据服务端稳定 seat 顺序相对本人排列，不得假定本人永远位于服务器座位 0；视觉上本人固定在底部，其余玩家按统一逆时针顺序分布。
5. 桌面攻防牌按公开结构和真实出牌者显示。多人同一轮的不同攻牌应能辨认是谁打出的，防牌归属防守方。

四、三人模式

1. 清楚显示一名防守方和两名进攻者；两名进攻者都属于独立玩家，不显示队友关系。
2. 根据 `currentActorId` 突出当前获得机会的玩家；玩家“过”后仍可能在别人合法出牌后重新获得跟牌机会，界面不得把其永久标成退出本轮。
3. 只有本人 `private.legalActionTypes` 中存在的动作才启用。非当前进攻者、等待防守或没有合法跟牌入口时不得提交抢行动作。
4. 防守方在服务端允许时可以收牌，包括已经压住部分或全部牌后收牌。
5. 独立终局应正确显示空手胜者，或憋王失败者的公开结果语义；如现有公开协议不足以安全区分失败者，只做最小协议扩展并补测试，禁止泄露手牌。

五、四人对家模式

1. 从公开 `team` 和 `role` 展示固定队伍：本人和对面座位是队友，左右两座是另一队。不得仅靠座位下标重新推断服务端队伍。
2. 明确显示本轮主攻、防守方、另一进攻者和旁观位。防守方的对家必须显示“旁观本轮/不能跟牌”，不能出现出牌、压牌或收牌入口。
3. 两名进攻者根据权威 `currentActorId` 轮流跟牌；客户端不得允许另一进攻者抢先提交。
4. 团队终局显示获胜队和失败队，并说明空手或憋王原因；本人所属队伍的胜负文案必须正确。
5. 任一身份持有主 2 且服务器允许时都能交换明牌；交换不改变倒计时。

六、动作与反馈

1. 继续覆盖 `play-card`、`beat-card`、`pass`、`collect` 和 `exchange-trump-two`，卡牌 ID 和防守目标必须来自当前权威快照。
2. 单牌选择、失败保留选择、成功后等待更高版本、重复提交保护及非法动作错误必须在所有人数模式一致。
3. 当前行动者、本人合法动作、队友/对手、进攻/防守/旁观角色、断线和最后 5 秒倒计时均需文字或图标辅助，不能只靠颜色。
4. 超时归零后只显示等待服务器处理，不在客户端自动过牌或收牌。
5. 断线恢复成功后重新校验选择；旧版本、旧连接或其他玩家消息不能覆盖当前本人视图。

七、响应式布局

1. 桌面端：三人形成上、左/右、本人底部的清晰关系；四人形成上/左/右/下牌桌，队友和对手一眼可辨。
2. 手机横屏 844×390 是核心目标：所有座位、桌面主要攻防牌、本人手牌、倒计时和关键动作按钮必须可见可点，不发生页面级水平溢出。
3. 手机竖屏仍能完成基本操作；可压缩非当前玩家信息和次要房间信息，但不能隐藏当前行动者、本人手牌或操作按钮。
4. 手牌较多、桌面攻牌达到上限、长昵称和浏览器安全区都需要验证。允许区域内部横向滚动，但必须提供明显可滚动边界，不能让按钮被手牌覆盖。
5. 遵守减弱动画偏好，不复制商业游戏素材。

八、协议与隐藏信息

1. 优先使用现有公开 `players.role/team/currentActorId/attackerId/defenderId/table`。若完成安全多人界面确实缺少字段，先用真实集成测试证明，再做最小共享协议和服务端投影扩展。
2. 公开终局扩展只能包含展示胜负所需的玩家/队伍 ID 和归一化原因，不得暴露内部引擎状态、手牌或牌墩顺序。
3. 所有入站消息继续经过共享 schema；DOM、日志、本地存储、分享链接和其他连接不得出现别人的手牌或任何重连令牌。

九、必须覆盖的测试

1. 本人位于每个可能座位时，三人和四人相对座位顺序均正确。
2. 三人两名进攻者的当前游标、过牌后重新跟牌、连续过牌结算与防守方收牌界面正确。
3. 四人队友、敌队、主攻、防守、另一进攻者和旁观位标识正确；旁观位无法提交游戏动作。
4. 三/四人所有允许动作使用正确 actionSequence、expectedStateVersion、cardId 和 targetCardId。
5. 主 2 交换在不同角色下可用且不重置 deadline。
6. 三人独立胜负/憋王失败和四人团队胜负/憋王失败文案正确。
7. 二人任务 16 的全部交互和布局继续回归通过。
8. 断线、刷新、恢复、连接替换和超时推进后，所有模式的座位、手牌、游标、deadline 与服务端一致。
9. 原始消息、DOM 与存储扫描确认无对手手牌、牌墩顺序和其他玩家令牌。
10. 二、三、四人各至少完成一局真实 WebSocket 浏览器对局；三人覆盖两名进攻者轮换，四人覆盖旁观对家与团队结算。
11. 桌面、844×390 横屏和 390×844 竖屏分别检查二、三、四人代表状态；包含最大手牌/桌面压力场景。
12. 现有 225 项及全部回归测试继续通过。

十、范围限制

本任务不实现聊天、观战者加入与观战 UI、战绩保存、完整结算历史、数据库或部署，这些属于任务 18–20。

允许修改 `apps/web`、必要的 `packages/ui`、相关测试和项目文档；只有安全多人显示确实需要时，才允许最小修改共享协议和服务端投影，并必须有回归测试。不得修改游戏规则语义或把权威引擎状态下发客户端。
```
