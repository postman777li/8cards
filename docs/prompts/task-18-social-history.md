# 任务 18 聊天、观战、战绩与结算提示词

将下面提示词完整复制到新的 Codex 窗口。

```text
你正在处理 E:\8Cards 中的“永城八张在线版”项目。

这是路线图任务 18：聊天、观战、战绩与结算。本窗口只能完成任务 18，不得提前实现任务 19 或 20。

一、开始前

1. 完整阅读 `AGENTS.md`、`docs/project-status.md`、`docs/TODO.md`、`docs/decisions.md`、`docs/architecture.md`、`docs/requirements.md`、`docs/game-rules.md` 和本提示词，并阅读房间、实时协议、权威投影、重连、网页会话及牌桌相关源码与测试。
2. 检查 `.codegraph/`；存在时理解或定位代码必须先使用 CodeGraph。
3. 确认 `main` 与 `origin/main` 同步且工作区没有其他窗口改动，从最新 `main` 创建 `feature/social-history`。
4. 在 `docs/project-status.md` 登记任务 18 进行中。先写清数据模型、存储边界、观战权限、聊天限制、结算与战绩原子性、隐私和测试计划，再开始实现。
5. 若数据库方案或产品语义存在歧义，记录并询问用户，不能静默猜测。不得修改游戏规则。

二、目标与范围

实现房间内文字聊天、只读观战、正式对局结算、访客战绩和对局记录，使玩家与观战者能安全看到允许的信息，并让服务端权威地记录每局结果。

本任务不包含完整系统弱网试玩、跨设备正式验收、Docker、公网部署、域名、HTTPS/WSS、监控或备份；这些属于任务 19、20。

三、存储与一致性

1. 先建立可替换的持久化接口，领域逻辑不能依赖进程内对象共享引用。开发实现可使用 SQLite；若实际引入 SQLite，需记录迁移方案和未来 PostgreSQL 适配边界。
2. 战绩与对局记录只能由服务端根据权威终局写入，客户端不得提交胜负、分数或牌局结果。
3. 同一对局结算必须幂等，重发、恢复、多个连接或进程内重复回调不能重复计入战绩。
4. 对局记录至少保存稳定对局 ID、房间/模式、参与玩家公开身份、座次/队伍、开始与结束时间、归一化结束原因、获胜/失败成员；不得保存重连令牌、完整牌墩、对手手牌或随机源。
5. 访客战绩按当前浏览器访客身份关联；第一版不承诺跨浏览器或跨设备恢复。明确删除房间和保留历史记录的生命周期差异。
6. 写入失败必须有明确策略和测试：不能向客户端宣告已持久化后静默丢失，也不能破坏已经完成的权威游戏状态。

四、文字聊天

1. 玩家和已加入房间的观战者可发送纯文本聊天；服务端验证身份、房间归属、长度、空白和频率限制。
2. 消息使用稳定 ID、发送者公开昵称/身份与服务器时间。禁止客户端伪造发送者、时间或系统消息。
3. 设置合理的 UTF-8 长度、房间内历史上限和单连接限流；超限返回稳定错误，不能拖垮广播或挤占游戏动作。
4. 前端必须按文本渲染，不能使用未净化 HTML；补 XSS、超长、重复、乱序、断线恢复与跨房间隔离测试。
5. 聊天失败不得阻塞或重置游戏倒计时，聊天也不得推进游戏公开版本，除非设计了独立聊天版本并记录决策。

五、观战

1. 设计严格的观战加入/恢复协议和容量限制。观战者不是玩家，不占座、不准备、不参与房主转移，也不能提交任何游戏动作。
2. 观战者只能收到 `SpectatorView` 允许的公共状态：公开玩家信息、牌数、角色/队伍、桌面牌、行动者、主牌、牌墩数量、倒计时和公开结算。
3. 任何情况下不得收到玩家私有手牌、牌墩顺序、重连令牌、内部引擎状态或可推导隐藏牌的数据。
4. 对局开始前后加入、刷新恢复、离开、连接替换、房间销毁和终局均要有明确行为。分享链接不得携带秘密凭证。
5. 网页提供清晰的观战身份和只读状态，不能显示可点击的出牌、压牌、过牌、收牌或主 2 交换入口。

六、结算与战绩 UI

1. 在二、三、四人终局展示正式结算：获胜/失败、空手或憋王原因、四人队伍结果、参与者和必要的公开统计。
2. 三人憋王没有唯一胜者时不得伪造冠军；四人失败队不得把两名成员都写成“本人触发憋王”。
3. 显示当前访客的累计局数、胜负和近期对局；所有统计从服务端记录计算或读取，不从 localStorage 自行累加。
4. 对局结束、刷新和恢复后结算内容一致；重复状态帧不能重复弹出或重复写战绩。
5. 电脑、844×390 手机横屏和 390×844 手机竖屏均可查看聊天、观战状态和结算，不能遮挡核心牌桌操作。

七、协议、安全与测试

1. 所有新事件使用共享严格 Zod schema、稳定错误码、动作序号/幂等语义，并明确哪些是单播、玩家广播、观战广播或历史查询响应。
2. 对玩家视图和观战视图做结构级隔离，服务端发送前再次 schema 校验。测试原始 WebSocket 帧、DOM、本地存储和日志中均无隐藏信息。
3. 覆盖二、三、四人正常空手、憋王和四人团队结算；覆盖重复结算、重连、连接替换、观战中途加入/离开、聊天限流和跨房间隔离。
4. 真实启动服务端与网页，至少以多个隔离浏览器完成一局包含玩家聊天、观战加入、刷新恢复、终局结算和战绩查询的流程，并复核 `/health`、控制台和进程清理。
5. 运行 `pnpm install --frozen-lockfile`、`pnpm typecheck`、`pnpm lint`、`pnpm format:check`、`pnpm test`、`pnpm test:coverage`、`pnpm build`、`git diff --check main...HEAD`。

八、文档与提交

更新 `docs/project-status.md`、`docs/TODO.md` 执行记录、`docs/architecture.md`、`docs/decisions.md` 以及必要的数据迁移说明，但不要勾选任务 18。若没有改变游戏规则，不修改 `docs/game-rules.md`。

提交并推送 `feature/social-history`，不要合并 `main`、不要创建 PR、不要开始任务 19。最终报告列出分支、提交 SHA、数据模型与存储方案、聊天和观战权限、结算幂等性、隐藏信息检查、测试/构建、真实浏览器流程、响应式证据、风险与未验证项，并提醒用户回总控窗口验收。
```
