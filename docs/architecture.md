# 系统架构规划

本文记录当前建议架构，尚未进入工程初始化阶段。

## 总体结构

计划采用 TypeScript 全栈单仓库：

```text
apps/
  web/          网页客户端
  server/       房间和实时游戏服务器
packages/
  game-engine/  纯游戏规则与状态机
  shared/       前后端共享类型和协议
  ui/           通用 UI 组件
docs/           项目文档
tests/          跨模块和联机测试
```

## 客户端

- React 和 TypeScript。
- 负责展示公开状态、玩家自己的手牌、动画和输入。
- 不负责洗牌、发牌、规则判定或胜负判定。
- 桌面端和手机端共享业务逻辑，牌桌重点适配手机横屏。

## 服务端

- Node.js 和 TypeScript。
- 使用 WebSocket 维持房间实时连接。
- 服务器权威处理房间、座位、倒计时、洗牌、发牌、出牌、压牌、收牌、补牌、轮转和结算。
- 每个动作带有递增序号或版本号，避免重复提交和乱序。
- 对每种连接只发送其有权查看的状态。

## 游戏引擎

- 使用确定性状态机表示游戏流程。
- 规则引擎不依赖网页或网络层，以便进行完整单元测试。
- 随机洗牌通过注入随机种子测试。
- 所有已确认规则必须具有正向和反向测试。

## 数据

- 开发阶段可使用 SQLite。
- 正式环境建议 PostgreSQL。
- 保存访客身份、房间摘要、对局结果、战绩和必要的重连状态。
- 聊天记录的保存期限需要后续决定。

## 部署

- 使用 Docker 保持平台可迁移性。
- 开发期可通过临时安全隧道进行零成本远程测试。
- 试玩阶段可使用支持 WebSocket 的托管平台。
- 正式阶段使用域名、HTTPS、WSS、数据库备份和错误监控。

## 安全

- 不向客户端或观战者发送无权查看的手牌。
- 昵称、聊天和房间输入均需校验和转义。
- 服务端验证所有游戏动作和行动者身份。
- 房间重连使用不可猜测的玩家令牌，不使用昵称作为身份凭证。
