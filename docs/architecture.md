# 系统架构规划

本文记录当前架构。任务 03 至 10 的工程、设计、协议、卡牌基础、二至四人规则状态机和规则引擎综合验收均已通过并合并到 `main`；房间、实时服务和其他业务模块仍待后续任务实现。

## 总体结构

计划采用 TypeScript 全栈单仓库：

```text
apps/
  web/          网页客户端
  server/       房间和实时游戏服务器
packages/
  game-engine/  纯游戏规则与状态机
  shared/       前后端共享类型和协议
  ui/           通用 UI 组件
docs/           项目文档
tests/          跨模块和联机测试
```

当前使用 pnpm workspace 管理 5 个 workspace。各应用和包分别维护入口、脚本与 TypeScript 配置，根目录统一提供开发、构建、类型检查、静态检查、测试和格式检查命令。单元测试当前与源码就近放置；未来跨模块测试可按需要增加 `tests/`。

## 客户端

- React 和 TypeScript。
- 使用 Vite 作为开发服务器和生产构建工具。
- 负责展示公开状态、玩家自己的手牌、动画和输入。
- 不负责洗牌、发牌、规则判定或胜负判定。
- 桌面端和手机端共享业务逻辑，牌桌重点适配手机横屏。

### UI 原型与设计系统

- `packages/ui/src/styles.css` 提供颜色、字体语境、间距、圆角、阴影、焦点态与减少动画等设计令牌和基础样式。
- `packages/ui/src/index.tsx` 提供按钮、面板、徽章、玩家座位和扑克牌基础组件；组件以语义化属性和状态修饰类表达视觉状态。
- `apps/web/src/App.tsx` 使用纯本地模拟数据组合首页、创建房间、等待房间、游戏牌桌和结算五个场景。
- `apps/web/src/navigation.ts` 定义原型场景清单及哈希地址解析，既支持页面内导航，也支持直接访问指定场景。
- 桌面端以 1440 × 900 为参考尺寸；手机端以 844 × 390 横屏为参考尺寸，并使用安全区、紧凑座位、精简操作区和重叠手牌布局。
- 原型层不调用后端接口，不实现规则判断、通信协议、房间服务、聊天、观战或战绩保存；这些能力仍由后续任务接入。

## 服务端

- Node.js 和 TypeScript。
- 基础工程仅使用 Node 原生 HTTP 提供 `/health` 健康检查；房间和 WebSocket 尚未实现。
- 使用 WebSocket 维持房间实时连接。
- 服务器权威处理房间、座位、倒计时、洗牌、发牌、出牌、压牌、收牌、补牌、轮转和结算。
- 每个动作带有递增序号或版本号，避免重复提交和乱序。
- 对每种连接只发送其有权查看的状态。

### 房间与访客会话核心

- `apps/server/src/room-service.ts` 提供不依赖 HTTP、WebSocket、连接对象或游戏引擎的同步领域服务。`RoomStore` 是窄存储边界，默认 `InMemoryRoomStore` 以房间 ID 和公开短码双索引保存存活房间，后续可替换持久化实现。存储读取总是返回独立记录，服务不依赖可变共享引用；每个成功转换都通过 `insert` / `update` / `delete` 显式提交。
- 生命周期为 `waiting` 与 `started`。等待期允许加入、准备和离开；开始后冻结座次与成员关系，房间核心只返回不可变的开局座次与配置，不创建游戏状态。
- 所有公开变更在单个同步调用内完成并恰好递增一次版本。依赖旧状态的写入要求 `expectedStateVersion`；存储提交另使用不对外公开的内部 `revision` 执行 compare-and-swap，因此公开状态或私有令牌的冲突写入都只有首次能原子成功。纯读取和在线状态未变的令牌旋转不改变公开版本，但仍递增内部修订并显式保存。
- 每名玩家拥有独立的安全随机重连令牌；存储层只保存 SHA-256 摘要，验证使用定时安全比较。恢复成功必定旋转令牌，旧令牌立即失效；错误房间、玩家或令牌对外统一为未授权。公开快照通过显式字段白名单构造，不含令牌、摘要或内部连接信息。

## 共享类型与实时协议

`packages/shared` 使用以下分层，并由 `@8cards/shared` 根入口统一导出：

- `common.ts`：带品牌的玩家、房间、对局、连接、请求和观战者标识，以及协议版本、状态版本、动作序号、时间戳和稳定错误码。
- `cards.ts`：54 张牌所需的花色、普通点数、大小王、卡牌标识和可判别卡牌结构；不包含牌力或合法性规则。
- `room.ts`：二至四人房间配置、玩家和观战者身份、座位、房主、在线与准备状态。
- `game-state.ts`：牌桌公开状态以及玩家本人、对手、观战者三种互不混用的视图。
- `events.ts`：客户端请求、服务端单播事件和公共广播事件，以及网络边界解析入口。
- `server-internal.ts`：服务端权威状态的类型边界；其中完整手牌、牌墩顺序、随机种子、重连令牌和内部连接标识不会出现在任何客户端事件 schema 中。

协议版本当前为 `1`。所有客户端请求带请求标识和正整数动作序号；依赖现有状态的请求另带预期状态版本。服务端响应通过请求标识关联，所有状态快照和公共增量事件带非负状态版本。

可见性由不同结构表达：公共快照只有手牌数量；玩家单播视图只附加该玩家自己的手牌和可用动作种类；对手及观战者视图没有私有字段。公共广播只允许公共快照和聊天等公开增量，不接受服务器权威状态。

所有跨网络事件使用 Zod 严格对象 schema 从 `unknown` 解析。未知类型、未知字段、错误枚举、错误字段类型和非法版本边界均拒绝；严格模式也防止敏感字段被静默剥离后继续流入应用。

## 游戏引擎

- 使用确定性状态机表示游戏流程。
- 规则引擎不依赖网页或网络层，以便进行完整单元测试。
- `packages/game-engine` 的卡牌基础层复用 `@8cards/shared` 的卡牌类型与运行时 schema，并由包根入口导出标准牌组、牌力比较、随机洗牌、明牌选择和初始轮抽 API。
- 标准牌组构造每次返回新的 54 张牌数组；牌力比较可表达王等值且最大、主牌高于副牌、同花色点数顺序，以及异花色副牌不可比较。
- 随机性通过 `RandomSource` 函数注入；洗牌使用返回新数组的 Fisher–Yates 算法，测试使用可重复的固定随机序列。
- 初始轮抽按传入座位数组的逆时针顺序逐张进行。牌墩以索引 0 为顶部、末项为底部；非王明牌从必经前缀选择，命中时不进入手牌、立即补抽，并在结束时置于牌墩末项。
- 当前基础层只负责创建牌、比较牌力、洗牌和初始发牌，不包含任务 07 的行动合法性、出牌回合或胜负状态机。
- 所有已确认规则必须具有正向和反向测试。
- 规则引擎综合验收使用固定种子的二、三、四人完整对局模拟，并对生产代码设置语句、函数、行 90% 和分支 85% 的 V8 覆盖率门槛。

### 二人规则状态机

- `packages/game-engine/src/two-player.ts` 从任务 06 的 `InitialDeal` 创建服务端权威二人状态，并由包根入口公开 `createTwoPlayerState`、`applyTwoPlayerAction`、状态/动作类型、稳定错误类型及不变量断言。
- 状态使用 `awaiting-attack`、`awaiting-defense`、`finished` 可判别联合；共同数据包含两名玩家座次、完整手牌、牌墩、弃牌区、固定主花色、当前底牌、攻守身份、桌面攻防牌对、可引点数、累计进攻数、换牌标记和状态版本。
- 普通动作是 `attack`、`defend`、`pass`、`take`；每个动作显式携带玩家身份。`take` 由当前防守方在桌面非空时发起，既可发生在尚未压牌的 `awaiting-defense`，也可发生在已压住一张或多张后的 `awaiting-attack`，因此不受普通行动者游标限制。`exchange-trump-two` 是不消耗行动权的独立动作，当前行动者与非当前行动者均可执行一次。
- 转换函数不修改输入。成功动作返回新状态并将版本递增一次；失败动作抛出带稳定错误码的 `TwoPlayerEngineError`，不会产生部分状态。
- 进攻与防守逐张交替，桌面普通攻牌和防守牌共同贡献可引点数；实时数量限制在每次进攻前根据防守方当前手牌重新判断。
- `pass` 原子完成防守成功结算、弃牌、进攻方优先补牌及攻守交换；`take` 原子完成桌面收牌、同样的补牌顺序，并保持原进攻方继续进攻。
- 每次手牌变化后的完成态检查先判断非空纯王手牌，再判断空手胜利。完成态拒绝后续游戏动作。
- 每次成功转换均验证 54 张牌无重复、无遗漏，并校验记录底牌与牌墩末项一致。该权威状态不属于共享网络视图，不能直接发送给客户端。

### 三人规则状态机

- `packages/game-engine/src/three-player.ts` 以独立多人模型提供 `createThreePlayerState`、`applyThreePlayerAction`、三人状态/动作/结果类型、稳定错误类及不变量断言，并由包根入口导出；它复用卡牌模型、`compareCards` 和桌面攻防牌对结构，不调用或伪造二人状态。
- 状态保存严格逆时针排列的三人座次、三手权威手牌、牌墩、弃牌区、底牌、主牌花色、本轮主攻、防守方、进攻游标、桌面攻防牌对、可引点数、累计进攻数、连续过牌数、主 2 交换标记和状态版本。
- 普通阶段仍按逐张 `awaiting-attack` / `awaiting-defense` 交替。防守成功后，进攻游标从刚出牌者沿逆时针跳过防守方移到另一进攻者；进攻者合法出牌将连续过牌数清零，连续两名进攻者过牌才原子结算防守成功。
- 防守方的 `take` 权限独立于进攻游标，只要桌面非空即可在待压牌或全部已压住时收牌。两名进攻者共享同一个累计进攻数，并按防守方实时剩余手牌共同受限。
- 结算补牌以结算前的本轮主攻为起点，沿完整三人座次逐人补至 8 张。防守成功时原防守方成为下轮主攻；收牌时跳过原防守方，由其下一座主攻再下一座防守。
- 三人结果是可判别联合：空手记录独立胜者，非空纯王记录独立失败者而不擅自指定胜者。每次成功转换按稳定座次先检查纯王失败、再检查空手胜利；若未来单次转换可能同时产生多个纯王失败，座次优先级仍须在任务 10 复核。
- 所有成功转换只递增一次版本并检查完整 54 张牌守恒；非法转换抛出 `ThreePlayerEngineError` 且不修改输入。该状态同样是服务器内部权威结构，不属于客户端协议。

### 四人规则状态机

- `packages/game-engine/src/four-player.ts` 提供独立四人权威状态机及根入口 API。座位严格按逆时针保存，0/2 与 1/3 分别组成固定队伍；状态显式记录主攻、防守方、防守方对家、两名有效进攻者及进攻游标。
- 每轮只有防守方能够压牌或收牌，其对家完全旁观。两名敌队进攻者轮流行动，游标跳过防守方及其对家；合法攻击清零连续过牌，两名进攻者连续过牌才完成防守成功结算，并共享桌面点数和实时累计攻击上限。
- 防守成功后原防守方成为下轮主攻；收牌后跳过原防守方，由其下一座主攻。两种结算都从结算前主攻开始，按完整四人座次补牌，因此旁观对家仍正常参与补牌。
- 团队结果同时记录获胜队、失败队、触发玩家及空手或憋王原因。非空纯王判负优先于空手获胜；潜在同时憋王仍以稳定座次扫描，并保留给任务 10 复核。
- 主 2 交换允许主攻、另一进攻者、防守方及旁观对家任一身份在未终局且牌墩非空时执行一次，不改变回合角色或游标。所有成功动作递增一次版本并验证完整 54 张牌守恒。

## 数据

- 开发阶段可使用 SQLite。
- 正式环境建议 PostgreSQL。
- 保存访客身份、房间摘要、对局结果、战绩和必要的重连状态。
- 聊天记录的保存期限需要后续决定。

## 部署

- 使用 Docker 保持平台可迁移性。
- 开发期可通过临时安全隧道进行零成本远程测试。
- 试玩阶段可使用支持 WebSocket 的托管平台。
- 正式阶段使用域名、HTTPS、WSS、数据库备份和错误监控。

## 安全

- 不向客户端或观战者发送无权查看的手牌。
- 昵称、聊天和房间输入均需校验和转义。
- 服务端验证所有游戏动作和行动者身份。
- 房间重连使用不可猜测的玩家令牌，不使用昵称作为身份凭证。
