# 系统架构规划

本文记录当前架构。任务 19 已通过验收并合并到 `main`；任务 20 正在 `release/first-online` 完成部署改造和公网发布。

## 总体结构

计划采用 TypeScript 全栈单仓库：

```text
apps/
  web/          网页客户端
  server/       房间和实时游戏服务器
packages/
  game-engine/  纯游戏规则与状态机
  shared/       前后端共享类型和协议
  ui/           通用 UI 组件
docs/           项目文档
tests/          跨模块和联机测试
```

当前使用 pnpm workspace 管理 5 个 workspace。各应用和包分别维护入口、脚本与 TypeScript 配置，根目录统一提供开发、构建、类型检查、静态检查、测试和格式检查命令。单元测试当前与源码就近放置；未来跨模块测试可按需要增加 `tests/`。

## 客户端

- React 和 TypeScript。
- 使用 Vite 作为开发服务器和生产构建工具。
- 负责展示公开状态、玩家自己的手牌、动画和输入。
- 不负责洗牌、发牌、规则判定或胜负判定。
- 桌面端和手机端共享业务逻辑，牌桌重点适配手机横屏。

### UI 原型与设计系统

- `packages/ui/src/styles.css` 提供颜色、字体语境、间距、圆角、阴影、焦点态与减少动画等设计令牌和基础样式。
- `packages/ui/src/index.tsx` 提供按钮、面板、徽章、玩家座位和扑克牌基础组件；组件以语义化属性和状态修饰类表达视觉状态。
- `apps/web/src/App.tsx` 使用纯本地模拟数据组合首页、创建房间、等待房间、游戏牌桌和结算五个场景。
- `apps/web/src/navigation.ts` 定义原型场景清单及哈希地址解析，既支持页面内导航，也支持直接访问指定场景。
- 桌面端以 1440 × 900 为参考尺寸；手机端以 844 × 390 横屏为参考尺寸，并使用安全区、紧凑座位、精简操作区和重叠手牌布局。
- 任务 04 的纯本地场景编排已在任务 14 被正式大厅入口取代；规则判断仍只由服务端执行，等待房、聊天、观战和战绩等能力由后续任务接入。

### 大厅入口

- `apps/web/src/realtime-client.ts` 是创建/加入房间的窄 WebSocket 边界，负责安全推导 `ws/wss` 地址、构造协议请求、使用 `@8cards/shared` 校验入站消息、关联响应并清理失败连接。React 组件不解析原始 WebSocket 消息。
- `apps/web/src/lobby.ts` 集中表单规范化、分享链接与本地存储边界。分享链接仅包含六位房间码；重连凭证按房间和玩家隔离保存。
- 大厅页面包含首页、创建房间和本地设置，并在任务 15 接入正式等待房；聊天和观战交互仍属于后续范围。

### 等待房客户端

- `apps/web/src/realtime-client.ts` 在创建、加入或恢复三件套握手后将同一 socket 交给持续会话对象；该对象集中校验服务器事件、维护严格递增动作序号、关联单个待处理操作，并只接受身份一致且版本不倒退的 `state.player`。
- React 等待房区分连接、等待、短暂断线、恢复、恢复失败与已开始状态。准备和开始按钮只提交服务端命令，不乐观修改成员状态；开始后的游戏视图仅进入任务 16 占位。
- 等待期返回首页先提交 `room.leave`，响应成功后才关闭 socket 并清除当前凭证；失败保持连接和凭证以便重试。断线、恢复失败及已开始状态不伪装普通离开成功，也不丢弃仍可能用于恢复的凭证。
- `apps/web/src/lobby.ts` 以当前会话索引定位按房间与玩家隔离的凭证。保存和读取均显式白名单化 `roomId/playerId/reconnectToken`，恢复成功后原子改存旋转令牌；连接对象、玩家视图和 socket 不进入本地存储。

### 二至四人游戏牌桌

- `apps/web/src/game-table.tsx` 只消费 `PlayerView`：本人手牌来自 `private.hand`，其他玩家仅展示公开昵称、座位、连接、角色、队伍和牌数；本地排序与单牌选择不改变卡牌 ID，也不实现牌力或胜负规则。
- 持续会话对象复用同一动作序号和最新公开版本提交共享 `GameAction`。游戏动作成功后，界面继续保持处理中，直到收到更高版本的权威 `state.player`；拒绝时保留原快照和选择。
- 客户端按公开稳定座次相对本人旋转：本人固定底部，三人其余两座位于左右上方，四人形成下、右、上、左关系。三人角色各自独立；四人队友、对手和旁观本轮标识直接来自公开 `team` 与 `role`，行动高亮只跟随 `currentActorId`。
- 桌面根据公开 `purpose` 结构配对攻防牌并显示每张攻牌的真实出牌者；倒计时只由权威 `turnDeadline` 显示，归零后等待服务器动作。断线、恢复和终局遮罩统一阻止提交。
- 桌面、844×390 手机横屏和 390×844 手机竖屏共用响应式布局；手牌与桌面压力区允许局部横向滚动，页面本身不产生水平溢出。

## 服务端

- Node.js 和 TypeScript。
- Node 原生 HTTP 提供 `/health` 健康检查，并由同一服务器承载 `/ws` WebSocket 实时服务。
- 使用 WebSocket 维持房间实时连接。
- 服务器权威处理房间、座位、倒计时、洗牌、发牌、出牌、压牌、收牌、补牌、轮转和结算。
- 每个动作带有递增序号或版本号，避免重复提交和乱序。
- 对每种连接只发送其有权查看的状态。

### 房间与访客会话核心

- `apps/server/src/room-service.ts` 提供不依赖 HTTP、WebSocket、连接对象或游戏引擎的同步领域服务。`RoomStore` 是窄存储边界，默认 `InMemoryRoomStore` 以房间 ID 和公开短码双索引保存存活房间，后续可替换持久化实现。存储读取总是返回独立记录，服务不依赖可变共享引用；每个成功转换都通过 `insert` / `update` / `delete` 显式提交。
- 生命周期为 `waiting` 与 `started`。等待期允许加入、准备和离开；开始后冻结座次与成员关系，房间核心只返回不可变的开局座次与配置，不创建游戏状态。
- 所有公开变更在单个同步调用内完成并恰好递增一次版本。依赖旧状态的写入要求 `expectedStateVersion`；存储提交另使用不对外公开的内部 `revision` 执行 compare-and-swap，因此公开状态或私有令牌的冲突写入都只有首次能原子成功。纯读取和在线状态未变的令牌旋转不改变公开版本，但仍递增内部修订并显式保存。
- 每名玩家拥有独立的安全随机重连令牌；存储层只保存 SHA-256 摘要，验证使用定时安全比较。恢复成功必定旋转令牌，旧令牌立即失效；错误房间、玩家或令牌对外统一为未授权。公开快照通过显式字段白名单构造，不含令牌、摘要或内部连接信息。

### WebSocket 实时层

- `apps/server/src/app.ts` 在同一 Node HTTP server 上保留 `GET /health`，并只在 `/ws` 接受 WebSocket 升级。传输使用 `ws`、16 KiB 最大消息、禁用压缩；二进制、坏 JSON、错误协议和严格 schema 失败均受控拒绝。
- 新连接没有身份，只能创建、加入房间或以序号 1 发送 `session.resume`。成功后 socket 绑定服务端保存的 `roomId/playerId/reconnectToken`；关闭当前有效 socket 会将玩家标为断线但持续保留座位和权威状态。恢复会验证并旋转令牌、同步本人完整私有视图，并原子替换仍存在的旧连接；旧连接关闭不会误伤新会话。同一恢复请求在同一连接重试会重放原响应和相同新凭证，不会二次旋转。
- 每个连接从动作序号 1 开始。只有通过 schema 且序号正好等于下一值的业务请求会执行并消耗序号，业务成功和业务失败都消耗；协议解析失败、旧序号、跳号和 ID 冲突不消耗。连接保存最多 64 个已处理请求的规范化内容与原始单播响应；完全相同重发只回放响应，不重执行业务、不重发凭证和状态。
- 请求发送顺序固定为关联的 `response.ok/error`、仅创建/加入者可见的 `session.established`（若有），最后逐连接生成 `state.player`。出站事件再次通过共享 schema 校验。
- 等待房公开版本等于 RoomService `stateVersion`。开局先通过 RoomService 的只读资格检查验证身份、版本、房主、人数、准备状态和等待期，再按座位升序用安全随机源构造二/三/四人权威状态，最后同步提交房间开始并安装 authority；资格或初始化失败均不改变房间。开局版本沿用房间版本，之后每个成功游戏动作使独立实时版本恰好加一，引擎内部版本只用于规则状态。
- `projection.ts` 是唯一状态投影入口。公共状态只包含房间、公开牌桌、角色、行动者、牌数、牌墩余量、权威 `turnDeadline` 和结果。实时房间通过可注入时钟/调度器维护唯一计时器；generation 只随行动机会变化或取消而变化，用于淘汰取消后仍触发的旧回调，不能绑定公开实时版本。开局及消耗行动机会的动作重置完整 20 秒，主 2 交换、断线和恢复不重置；到期按阶段自动 `pass` 或 `collect`，掉线玩家的回合照常推进。每个玩家的单播视图只附加本人手牌和权威动作种类。

## 共享类型与实时协议

`packages/shared` 使用以下分层，并由 `@8cards/shared` 根入口统一导出：

- `common.ts`：带品牌的玩家、房间、对局、连接、请求和观战者标识，以及协议版本、状态版本、动作序号、时间戳和稳定错误码。
- `cards.ts`：54 张牌所需的花色、普通点数、大小王、卡牌标识和可判别卡牌结构；不包含牌力或合法性规则。
- `room.ts`：二至四人房间配置、玩家和观战者身份、座位、房主、在线与准备状态。
- `game-state.ts`：牌桌公开状态以及玩家本人、对手、观战者三种互不混用的视图。
- `events.ts`：客户端请求、服务端单播事件和公共广播事件，以及网络边界解析入口。
- `server-internal.ts`：服务端权威状态的类型边界；其中完整对手手牌、牌墩顺序、随机种子、令牌摘要和内部连接标识不会出现在客户端状态或公共事件 schema 中。任务 12 可新增仅向令牌本人发送的一次性严格凭证事件，但不得广播或写入状态快照。

协议版本当前为 `1`。所有客户端请求带请求标识和正整数动作序号；依赖现有状态的请求另带预期状态版本。服务端响应通过请求标识关联，所有状态快照和公共增量事件带非负状态版本。

可见性由不同结构表达：公共快照只有手牌数量；玩家单播视图只附加该玩家自己的手牌和可用动作种类；对手及观战者视图没有私有字段。公共广播只允许公共快照和聊天等公开增量，不接受服务器权威状态。

所有跨网络事件使用 Zod 严格对象 schema 从 `unknown` 解析。未知类型、未知字段、错误枚举、错误字段类型和非法版本边界均拒绝；严格模式也防止敏感字段被静默剥离后继续流入应用。

## 游戏引擎

- 使用确定性状态机表示游戏流程。
- 规则引擎不依赖网页或网络层，以便进行完整单元测试。
- `packages/game-engine` 的卡牌基础层复用 `@8cards/shared` 的卡牌类型与运行时 schema，并由包根入口导出标准牌组、牌力比较、随机洗牌、明牌选择和初始轮抽 API。
- 标准牌组构造每次返回新的 54 张牌数组；牌力比较可表达王等值且最大、主牌高于副牌、同花色点数顺序，以及异花色副牌不可比较。
- 随机性通过 `RandomSource` 函数注入；洗牌使用返回新数组的 Fisher–Yates 算法，测试使用可重复的固定随机序列。
- 初始轮抽按传入座位数组的逆时针顺序逐张进行。牌墩以索引 0 为顶部、末项为底部；非王明牌从必经前缀选择，命中时不进入手牌、立即补抽，并在结束时置于牌墩末项。
- 当前基础层只负责创建牌、比较牌力、洗牌和初始发牌，不包含任务 07 的行动合法性、出牌回合或胜负状态机。
- 所有已确认规则必须具有正向和反向测试。
- 规则引擎综合验收使用固定种子的二、三、四人完整对局模拟，并对生产代码设置语句、函数、行 90% 和分支 85% 的 V8 覆盖率门槛。

### 二人规则状态机

- `packages/game-engine/src/two-player.ts` 从任务 06 的 `InitialDeal` 创建服务端权威二人状态，并由包根入口公开 `createTwoPlayerState`、`applyTwoPlayerAction`、状态/动作类型、稳定错误类型及不变量断言。
- 状态使用 `awaiting-attack`、`awaiting-defense`、`finished` 可判别联合；共同数据包含两名玩家座次、完整手牌、牌墩、弃牌区、固定主花色、当前底牌、攻守身份、桌面攻防牌对、可引点数、累计进攻数、换牌标记和状态版本。
- 普通动作是 `attack`、`defend`、`pass`、`take`；每个动作显式携带玩家身份。`take` 由当前防守方在桌面非空时发起，既可发生在尚未压牌的 `awaiting-defense`，也可发生在已压住一张或多张后的 `awaiting-attack`，因此不受普通行动者游标限制。`exchange-trump-two` 是不消耗行动权的独立动作，当前行动者与非当前行动者均可执行一次。
- 转换函数不修改输入。成功动作返回新状态并将版本递增一次；失败动作抛出带稳定错误码的 `TwoPlayerEngineError`，不会产生部分状态。
- 进攻与防守逐张交替，桌面普通攻牌和防守牌共同贡献可引点数；每轮开始保存防守方手牌数为固定累计进攻上限，压牌后不再下降。
- `pass` 原子完成防守成功结算、弃牌、进攻方优先补牌及攻守交换；`take` 原子完成桌面收牌、同样的补牌顺序，并保持原进攻方继续进攻。
- 每次手牌变化后的完成态检查先判断非空纯王手牌，再判断空手胜利。完成态拒绝后续游戏动作。
- 每次成功转换均验证 54 张牌无重复、无遗漏，并校验记录底牌与牌墩末项一致。该权威状态不属于共享网络视图，不能直接发送给客户端。

### 三人规则状态机

- `packages/game-engine/src/three-player.ts` 以独立多人模型提供 `createThreePlayerState`、`applyThreePlayerAction`、三人状态/动作/结果类型、稳定错误类及不变量断言，并由包根入口导出；它复用卡牌模型、`compareCards` 和桌面攻防牌对结构，不调用或伪造二人状态。
- 状态保存严格逆时针排列的三人座次、三手权威手牌、牌墩、弃牌区、底牌、主牌花色、本轮主攻、防守方、进攻游标、桌面攻防牌对、可引点数、累计进攻数、连续过牌数、主 2 交换标记和状态版本。
- 普通阶段仍按逐张 `awaiting-attack` / `awaiting-defense` 交替。防守成功后，进攻游标从刚出牌者沿逆时针跳过防守方移到另一进攻者；进攻者合法出牌将连续过牌数清零，连续两名进攻者过牌才原子结算防守成功。
- 防守方的 `take` 权限独立于进攻游标，只要桌面非空即可在待压牌或全部已压住时收牌。两名进攻者共享同一个累计进攻数和轮开始时的固定上限。
- 结算补牌以结算前的本轮主攻为起点，沿完整三人座次逐人补至 8 张。防守成功时原防守方成为下轮主攻；收牌时跳过原防守方，由其下一座主攻再下一座防守。
- 三人结果是可判别联合：空手记录独立胜者，非空纯王记录独立失败者而不擅自指定胜者。每次成功转换按稳定座次先检查纯王失败、再检查空手胜利；若未来单次转换可能同时产生多个纯王失败，座次优先级仍须在任务 10 复核。
- 所有成功转换只递增一次版本并检查完整 54 张牌守恒；非法转换抛出 `ThreePlayerEngineError` 且不修改输入。该状态同样是服务器内部权威结构，不属于客户端协议。

### 四人规则状态机

- `packages/game-engine/src/four-player.ts` 提供独立四人权威状态机及根入口 API。座位严格按逆时针保存，0/2 与 1/3 分别组成固定队伍；状态显式记录主攻、防守方、防守方对家、两名有效进攻者及进攻游标。
- 每轮只有防守方能够压牌或收牌，其对家完全旁观。两名敌队进攻者轮流行动，游标跳过防守方及其对家；合法攻击清零连续过牌，两名进攻者连续过牌才完成防守成功结算，并共享桌面点数和固定轮累计攻击上限。

### 任务 21 连续排名与房间赛

- 实时房间保存公开赛程阶段、局数、倍率、积分、胜负、连胜、继续投票与当前出完顺序；客户端只渲染权威投影。
- 普通空手完成后由实时权威层保留卡牌集合并把四人状态转换为三人状态、再转为二人状态；已出完玩家以公开 0 手牌旁观，直到完整名次产生。憋王仍走原即时终局路径。
- 单局完成进入继续投票；全员继续时保持房间码、玩家和座位，重新洗牌并公开下一局倍率。任意停止或弃权结束整场。
- 等待房换座由 `RoomService` 原子保存请求；协议采用版本、动作序号和严格 schema，成功后重置参与者准备状态。
- `room_series` 迁移表只保存最终公开汇总，不保存进行中手牌、牌墩、令牌或连接；应用重启仍会丢失进行中的赛程。
- 防守成功后原防守方成为下轮主攻；收牌后跳过原防守方，由其下一座主攻。两种结算都从结算前主攻开始，按完整四人座次补牌，因此旁观对家仍正常参与补牌。
- 团队结果同时记录获胜队、失败队、触发玩家及空手或憋王原因。非空纯王判负优先于空手获胜；潜在同时憋王仍以稳定座次扫描，并保留给任务 10 复核。
- 主 2 交换允许主攻、另一进攻者、防守方及旁观对家任一身份在未终局且牌墩非空时执行一次，不改变回合角色或游标。所有成功动作递增一次版本并验证完整 54 张牌守恒。

### 任务 22 精品体验层

- `audio-system.ts` 使用 Web Audio 合成短促提示音，按权威版本键去重；音效不可用、页面隐藏或未解锁时不影响动作。
- `experience.ts` 集中快捷语、固定表情枚举、公开抽牌差量与标准并列排名。牌墩到座位的动画不读取牌面，恢复时直接收敛到最新快照。
- `reaction.send` / `reaction.show` 是不保存历史的最小公开事件；服务端验证身份、枚举、版本、序号与限流，并向玩家和观战者广播。
- 结算使用单局分差、倍率、投票进度与最终排名分层展示；同分采用 `1, 1, 3` 标准名次，金银铜徽章和称号徽章均为原创 CSS。

## 数据

- 任务 18 开发环境使用 Node.js 原生 SQLite，默认文件为 `data/8cards.sqlite`，测试使用独立内存库。
- `HistoryStore` 隔离事务和 SQL 方言；`games.game_id` 唯一约束与同事务参与者写入提供最终幂等性。领域层只接触归一化对局记录和访客查询结果。
- 对局记录保存公开房间摘要、模式、参与者、座次、队伍、开始/结束时间、原因与胜负/未决结果；不保存手牌、牌墩顺序、随机源或凭证。
- 聊天是运行中房间的有界内存数据，独立 `chatVersion`，最多 100 条，房间销毁即删除。
- 正式环境建议 PostgreSQL。
- 保存访客身份、房间摘要、对局结果、战绩和必要的重连状态。
- PostgreSQL 迁移只替换 `HistoryStore` 适配器及迁移脚本；实时房间、权威状态和聊天生命周期不在本任务持久化。

### 任务 18 社交实时层

- 玩家与观战者使用不同身份联合。观战者拥有独立随机凭证及摘要、刷新旋转和连接替换语义；每房最多 20 个观战身份，等待房和对局中均可加入。
- `SpectatorView` 从公共快照白名单直接构造，没有 `private` 字段。实时层对所有玩家和观战出站事件再次执行共享严格 schema 校验。
- 聊天发送者、服务器时间、稳定消息 ID 和版本均由服务端生成。单条同时限制 300 字符和 1,200 UTF-8 字节，并拒绝危险控制字符；每身份十秒最多五条。
- 权威引擎首次进入终局后构造一次归一化记录并调用历史存储。重复终局或恢复依赖 `game_id` 唯一约束去重；保存失败不回滚权威终局，历史响应明确返回等待保存状态并允许查询触发重试。

## 部署

- 使用多阶段 Docker 构建；运行镜像以非 root 用户启动，内置健康检查和 PostgreSQL 客户端，不包含源码、开发工具或真实秘密。
- Node.js 在同一端口提供 React 生产产物、`/health` 存活检查、`/ready` 数据库就绪检查和 `/ws`，避免跨域并保证 HTTPS 页面只连接 WSS。
- 预发布采用 Render 新加坡免费单实例与 Neon 新加坡 PostgreSQL；`render.yaml` 固定单实例、关闭自动部署并配置健康检查，真实秘密由平台注入。
- 最终生产目标为腾讯云中国大陆单应用实例与托管 PostgreSQL，完成域名、ICP 备案、公安联网备案、HTTPS/WSS、监控和备份后切换。
- `SIGTERM`/`SIGINT` 会停止接入、取消计时器、终止 WebSocket、关闭数据库连接并在平台 30 秒终止窗口内退出。
- 日志为结构化 JSON，并对令牌、密码、连接串、Cookie、Authorization 和私钥字段脱敏；不记录协议消息体、手牌或牌墩。
